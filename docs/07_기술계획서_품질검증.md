- **F5는 F1을 기다리지 않는다**: F0에서 스키마를 고정하면 평가 쪽은 하드코딩 픽스처(`tests/fixtures/features_yeoksam_20261.json`)로 D2부터 시작한다. F1이 끝나면 픽스처를 실제 함수 호출로 교체만 하면 된다.

## 3. 시스템 아키텍처

```
[프론트] ──> [FastAPI 단일 서비스]
              ├─ src/app_core/generation/   ← 기본 파이프라인 (nlu·copy_gen·image_gen·layout·compliance)
              └─ src/app_core/panel/        ← 품질 검증 (features·panel_builder·evaluator)
                   ├─ DuckDB 파일 (상권 피처 + 평가 로그)
                   ├─ LLM API (패널 서사 1콜 + 평가 ≤20콜)
                   └─ Kakao Local API (주소→좌표→행정동)

호출 경계:  완성 광고물 + context ──> evaluate() ──> EvaluationResult ──(suggestions)──> 재생성
```

- 패널 모듈은 **기본 파이프라인 코드를 import하지 않는다.** 계약은 §5.1 함수 시그니처와 §6 스키마뿐이고, 반대 방향도 함수 하나로만 부른다.
- 상태는 **DuckDB + 세션 쿠키(UUID)**로만 관리. 서버 메모리 세션 없음.
- 배포·인프라(Docker Compose·nginx·GCP VM)는 **팀 공통** — 이 문서의 명세 대상 아님. GPU는 이미지 생성(SDXL)이 쓴다.
- 공유 파일 주의: `configs/*.yaml`·`flow.yaml`은 기본 파이프라인 소유. 업종 추가가 필요하면 PR 전에 공유.

### 4.4 CSV 실물 검수 결과 (2026-08-06 완료) — §6 스키마의 근거

**최신 분기 = `20261`(2026년 1분기).** 추정매출·점포는 20251~20261, 길단위인구는 2021Q1~2026Q1 수록.

**① 성별×연령 교차 데이터가 없다 (설계 영향 큼)**
원본은 `남성_매출_금액`/`여성_매출_금액`과 `연령대_30_매출_금액`이 **따로** 있고, "30대 여성 매출"은 존재하지 않는다.
→ `gender_share`·`age_share` 두 축으로 분리하고, 페르소나 `weight`는 **두 축의 곱**(독립 가정)으로 만든다.
→ `evidence`는 곱한 값이 아니라 **원본 두 값을 각각 인용**하게 해서(`gender_share.F` + `age_share.30`) 근거 대조가 실제 데이터와 1:1로 맞게 한다. 독립 가정은 실제 상관을 무시하므로, 페르소나 가중치는 "정확한 인구수"가 아니라 **상대적 비중**으로만 쓴다.

**② 성별·연령 합계가 1이 아니다 (미상 매출)**
요식업·카페 6,573행 기준 합계 평균 **0.879**, 중앙값 0.918, 최소 0.065 (법인카드·비식별 결제 추정). 성별합과 연령합은 항상 일치.
→ 합계로 나눠 정규화하고, 그 합계를 `demo_coverage`로 보존한다. **0.5 미만이면(전체의 1.2%) 결과 화면에 신뢰도 낮음 표시.**

**③ 유동인구 ≠ 구매층 — 시간대는 매출 기준을 쓴다**
역삼역 커피-음료 기준, 유동인구 시간대는 평탄(최고 06-11의 0.215)한데 **매출은 11-14가 0.479로 압도적**이다. "지나다니는 사람"과 "사는 사람"이 다르다.
→ `time_share`는 **매출 시간대**로 만든다. 유동인구는 `foot_age_share`(연령 도달층)만 남겨 **경계 페르소나 근거**로 쓴다.

연령별로 보면 차이가 더 분명하다 (역삼역, 2026Q1).

| 연령 | 유동인구 | 카페 매출 | 매출/유동 |
|---|---|---|---|
| **10대** | 3.9% | **0.3%** | **0.09배** |
| 20대 | 21.6% | 16.2% | 0.75배 |
| 30대 | 30.0% | 38.2% | 1.27배 |
| 40대 | 22.7% | 22.1% | 0.97배 |
| 50대 | 12.6% | 15.1% | 1.19배 |
| 60대+ | 9.2% | 8.1% | 0.88배 |

**"지나다니지만 사지 않는 층"은 10대·20대다.** 30·50대는 반대로 유동보다 매출 비중이 높은 실구매층이다.
`foot_age_share / age_share` 비율이 낮은 연령대가 곧 경계 페르소나 후보이며, 이 비율 자체가 근거 수치가 된다.

> ⚠️ 초판(2026-08-06)에 "60대 유동 12.4% vs 매출 8.1%"로 적었던 것은 **오류**였다. `foot_age_share`를 실제로 계산하지 않고 손으로 지어낸 픽스처 값을 인용한 것이다. 실제 60대 격차는 1.1%p로 미미하다. 현재 값은 `build_features()`가 DuckDB에서 직접 계산한다.

**④ 좌표계가 WGS84가 아니다**
`엑스좌표_값` 182,509~215,352 / `와이좌표_값` 437,249~465,573 → 중부원점TM(EPSG:5181 계열). 카카오 API는 WGS84를 반환하므로 변환 필요(`pyproj`).
→ 완화책: 영역-상권에 `행정동_코드`가 있으므로 **카카오 `coord2regioncode`로 행정동을 받아 1차 필터 → 그 안에서만 거리 비교**하면 좌표 변환 오차의 영향이 줄어든다.

**⑤ 컬럼명 차이·오타**
- `점포_수` → 실제는 `전체_점포_수` (`일반_`/`프랜차이즈_`/`개업_`/`폐업_점포_수` 별도)
- 원본 오타: `시간대_건수~06_매출_건수` (`시간대_00~06_매출_건수`여야 함). 매출 **금액** 컬럼은 정상.

**⑥ 데이터 노후화 영향 실측 — 무시 가능**
같은 1분기끼리 비교한 연령·성별 비중의 평균 절대 변화(상권 1,649개):

| 비교 | 변화 폭 |
|---|---|
| 2025Q1 → 2026Q1 (1년) | 0.54~0.88%p |
| 2024Q1 → 2025Q1 (1년) | 0.53~0.84%p |
| **2021Q1 → 2026Q1 (5년)** | **1.11~2.02%p** |

상권의 인구 구성은 5년이 지나도 2%p 안쪽으로만 움직인다. 분기 지연(약 2분기)은 페르소나 가중치에 유의미한 영향을 주지 않는다. 단, 결과 화면에 **"2026년 1분기 서울시 상권분석 데이터 기준"**을 표기해 신선도를 오해하지 않게 한다.

### 4.6 근거 등급 — 무엇이 데이터고 무엇이 추론인가

이 모듈이 내놓는 값의 출처가 섞여 있다. **섞인 채로 "상권 그라운딩"이라고 뭉뚱그리면 과장이 된다.** 등급을 나눠 명시하고, 결과 화면 문구도 여기에 맞춘다.

| 항목 | 출처 | 등급 |
|---|---|---|
| 성별·연령 구성 (`gender_share`·`age_share`) | 카드 매출 실적 | **A. 실측** |
| 시간대·주말 패턴 (`time_share`·`weekend_ratio`) | 매출 실적 | **A. 실측** |
| 객단가·경쟁 점포 수 | 매출·점포 실적 | **A. 실측** |
| 유동인구 연령 (`foot_age_share`) | 통신 기반 추정 | **A. 실측**(추정치임을 명시) |
| 직장·상주인구, 상권 성격 (`work_ratio`) | 인구 실적 | **A. 실측** — 2026-08-07 추가 |
| 배후 주거 가격대 (`apt_avg_price`) | 공시 시가 | **A. 실측** — 2026-08-07 추가 |
| 가격 민감도 (`price_sens`) | 객단가 분위 + 배후 아파트 시가 | **B. 추론** — 근거가 둘로 늘었으나 여전히 동네 평균이지 개인 성향이 아니다 |
| 방문 동기 (`motive`) | `work_ratio` + 시간대 집중도 | **B. 추론** — "점심에 팔리니 직장인 상권"이라는 추론이 직장인구 실측으로 바뀌어 근거가 단단해졌다 |
| 페르소나 서사 (`narrative`) | LLM 생성 | **C. 창작** — 코멘트 가독성을 위한 것이지 판단 근거가 아니다 |
| 평가 점수 (`attention`·`message`·`intent`) | LLM 판단 | **C. 창작** — 근거 대조를 통과한 것만 집계하지만, 점수 자체는 검증된 값이 아니다 |

**A는 광고와 무관하게 결정되고, C는 A를 인용하도록 강제한다**(§8 근거 대조). 그래서 C가 A를 벗어나면 탈락한다. 하지만 그것이 "점수가 맞다"는 뜻은 아니다 — **일관성 보증이지 정확도 보증이 아니다.**

**우리가 검증할 수 없는 것**: 이 패널의 점수가 실제 손님 반응과 일치하는지. 실제 광고 반응 정답지가 없다. `eval/panel_metrics.py`(상관계수·MAE)는 정답지가 생겼을 때를 위한 도구이고, 현 단계에서는 대조할 대상이 없다.

→ **따라서 제품 문구는 예측이 아니라 점검으로 쓴다.** "손님이 이렇게 반응합니다"(❌) / "이 광고는 이 동네 매출의 38%를 차지하는 30대에게 닿지 않습니다"(✅). 뒤 문장은 A 등급만으로 성립한다.

**유효 표본 수**: 페르소나는 12개지만 가중치가 쏠려 실질 표본은 그보다 작다. 서울 카페 상권 1,064곳 기준 **평균 7.9 / 중앙값 8.3**(Kish 유효 표본), 41%의 상권이 8 미만이고 최악은 1.0이다(한 세그먼트가 거의 전부). 이 값을 피처에 실어 **패널 구성 자체의 쏠림**도 신뢰도 판단 근거로 쓴다 — 지금은 응답 분산만 보고 있다.

**세그먼트 내 이질성은 0이다.** 같은 "30대 여성"은 한 명뿐이라 그 층의 의견 폭을 표현하지 못한다. 페르소나를 20개·50개로 늘려도 인구 구성이 쏠려 있어 유효 표본은 거의 안 오른다. → 남는 콜 예산은 **유형 추가가 아니라 동일 유형 반복 샘플링**에 쓴다(§8). 같은 페르소나를 두 번 물어 답이 갈리면 그것은 "손님 간 이견"이 아니라 **모델 노이즈**이며, 이 둘을 구분할 수 있어야 분산 체크가 의미를 갖는다.

### 5.1 계약 — 기본 파이프라인과의 경계 ⭐ (2026-08-07 개정)

[05 최종계획서 §7-5](05_최종계획서.md)의 주문서 구조를 **그대로 받는다. 추가 요청 없음.**

> ✅ **주소 요청은 이미 해결됐다.** 05 §2에서 가게 등록 시 주소를 받고, `StoreInput.address`는 기본값 `"서울"`에 서울 외 주소를 막는 검증까지 걸려 있어 **항상 값이 존재한다.** 앞선 개정판에서 요청했던 `context.store_address`는 필요 없어졌다.

```python
def evaluate(
    store: Store,                  # app_core.schema — 업종·주소·상호
    brief: AdBrief,                # app_core.schema — 상품·가격·상황·톤
    copies: list[AdCopy],          # 생성된 문구 후보 중 사용자가 고른 1건
    image: PIL.Image | None = None,  # 최종 PNG (현재 미사용, §아래)
) -> EvaluationResult:             # §6
```

**우리가 쓰는 필드** (나머지는 무시한다 — 저쪽이 필드를 늘려도 우리 코드는 안 깨진다)

| 필드 | 용도 |
|---|---|
| `store.address` | 상권 매칭 → 페르소나 구성 |
| `store.industry` | 업종별 피처 선택 (§4.5 매핑) |
| `store.industry_label` | 프롬프트에 넣는 사람 읽는 업종명. `other`면 사장님이 적은 값 |
| `brief.product` · `price` · `situation` · `tone` | 평가 프롬프트의 광고물 설명 |
| `brief.show_price` | 0원이면 가격 언급 자체를 평가에서 뺀다 |
| 선택된 문구의 `headline` · `sub` | 평가 대상 본문 |

**폐기된 필드** — 04 문서 기준이던 `format`·`style`·`mode`·`legal_tags`·`session_id`는 05에서 사라졌다. 우리는 `format`·`style`을 **어차피 쓰지 않기로 했었으므로**(채널별 도달 보정은 근거 데이터가 없다, [06 §6](06_AI손님패널_기획.md)) 손실이 없다.

**설계 전제가 하나 좋아졌다.** 주소를 **가게 등록 시점**에 받으므로 광고를 만들기 전에 이미 확보돼 있다. 패널을 미리 만들어 `stores.id` 기준으로 캐시해두면, 평가 요청 시 패널 구성(LLM 1콜 + 상권 조회)을 건너뛸 수 있다 → 30초 예산에 여유가 생긴다.

**이미지는 현 단계에서 평가에 쓰지 않는다.** 비전 콜은 콜 수·비용·응답 시간을 모두 늘린다. 문구·가격·컨텍스트만으로 평가하고, 시각 품질 평가는 여력이 남으면 비전 1콜 옵션으로 추가한다. 인자는 인터페이스 안정성을 위해 지금 받아둔다.

**문구 후보 3건 중 1건만 평가한다** — 3건 전부면 비용·시간이 3배다 ([06 §6-2](06_AI손님패널_기획.md)).

### 5.2 패널 모듈 API (FastAPI, `/api` 프리픽스)

| 메서드/경로 | 요청 | 응답 | 비고 |
|---|---|---|---|
| POST `/panel/build` | `{store_id}` | `{panel_id, features, personas[]}` | R1. 가게 등록 직후 호출 → 캐시 |
| PATCH `/panel/{id}/weights` | `{persona_id: weight}[]` | 갱신된 personas | 합=1 정규화는 서버가 |
| POST `/evaluate` | `{store_id, ad_id, copy_id}` | `EvaluationResult` | R4·R5. 평가 한도 차감. store·brief·copy는 서버가 DB에서 읽는다 |
| POST `/events` | `{event_type, payload}` | 204 | R8 |
| GET `/usage` | — | `{eval_used, eval_limit}` | R9 |

- **05 최종계획서의 DB(PostgreSQL)에 이미 `stores`·`ads`·`ad_copies`가 있으므로 프론트가 본문에 실어 보낼 필요가 없다.** id만 받고 서버가 조회한다.
- 재생성은 **이 모듈의 API가 아니다.** 프론트가 `EvaluationResult.suggestions`를 들고 기본 파이프라인의 재생성 엔드포인트를 호출한다 (R7).
- 사용량 식별은 로그인 계정(`users.id`) 기준. 05에서 로그인이 생겨 세션 쿠키가 필요 없어졌다.
- 에러 규약: `{error_code, user_message}` — user_message는 사장님 언어(전문용어 금지). 코드: `NO_TRADE_AREA` / `EVAL_LIMIT_EXCEEDED`.
  ~~`OUT_OF_SEOUL`~~은 가게 등록 단계에서 막히고, ~~`UNSUPPORTED_INDUSTRY`~~는 폴백으로 대체됐다(§4.5).

```python
    avg_ticket: int                                # 객단가(원) = 당월_매출_금액/당월_매출_건수
    avg_ticket_pct: float                          # 서울 동일 업종 내 분위 (0~1) — price_sens 판정용
    competitor_cnt: int                            # 동일 업종 전체_점포_수

    work_ratio: float | None                       # 직장/(직장+상주). 1에 가까우면 출퇴근 상권
    household_cnt: int
    apt_cnt: int                                   # 상권 안 아파트 단지 수
    apt_avg_price: int | None                      # 아파트 평균 시가(원) — 소득 축 대리. 없으면 None

    persona_id: str
    demo: str                                      # "30대 여성"
    axes: dict[str, str]                           # {"price_sens":"mid","motive":"habitual","time":"weekday_lunch"}
    weight: float                                  # 인구 비중 기반, 패널 내 합=1
    is_boundary: bool                              # 경계 페르소나 여부
    narrative: str                                 # LLM 생성 1~2문장

    path: str                                      # "age_share.30" / "time_share.11-14"

class PersonaEval(BaseModel):

    attention: int; message: int; intent: int      # 0~100
    resistance: Literal["price","message","visual","relevance","none"]
    resistance_detail: str
    comment: str                                   # 1줄, 사장님 언어
    evidence: list[FeatureRef]                     # 필수 — 없으면 스키마 검증 실패

class EvaluationResult(BaseModel):
    ad_id: str
    scores: dict[str, float]                       # 가중 평균 3종
    confidence: Literal["ok","low"]                # 분산 체크 결과
    top_resistance: list[str]
    suggestions: list[str]                         # 재생성 입력으로 그대로 전달
    persona_comments: list[PersonaEval]            # 검증 통과분만
    excluded_cnt: int                              # 근거 대조 탈락 수 (투명성)
```

## 7. LLM 파이프라인 명세

| 단계 | 콜 수 | 출력 강제 |
|---|---|---|
| 패널 서사 생성 | 패널당 1콜 (유형 전체 배치) | JSON mode → Persona[] 부분 필드 |
| 패널 평가 | 시안당 ≤20콜 (병렬) | JSON mode → PersonaEval |

- **패널 모듈이 쓰는 LLM 콜은 이 둘뿐이다.** 생성·추출 콜은 전부 기본 파이프라인 소관.
- 모델·단가는 구현 시점 재확인. temperature: 평가=0.3(일관성), 서사=0.8.

### 7.1 패널 빌더 — 축 값 유도 룰 (전부 코드, LLM 미개입)
- **인구축**: `gender_share` × `age_share` 곱 → 최대 10개 세그먼트(성별 2 × 연령 5). **비중 3% 미만은 인접 연령대로 병합** (역삼역 사례에서 10대 0.3% → 20대로 병합).
- **시간대 맥락**: `time_share`(매출) 상위 구간 → weekday_lunch / afternoon / evening / morning (weekend_ratio > 0.4면 weekend 유형 추가)
- **가격 민감도**: `avg_ticket_pct` → <0.25 low / 0.25~0.75 mid / >0.75 high (상권 객단가가 높을수록 그 동네 손님의 가격 저항이 낮다는 뜻)
- **방문 동기**: 주중·특정 시간대 집중이면 habitual, 주말·분산이면 exploratory
- 세그먼트 = 인구축 × 행동축. **유형 수 10~20 유지** — 상위 인구 세그먼트 1~2개만 행동축으로 분할한다. 데이터 근거 없는 세분화(환각 다양성) 금지.
- **경계 페르소나 1~2개 필수**: `age_share / foot_age_share` 비율이 가장 낮은 연령대 — **지나다니지만 사지 않는 층**이다(역삼역 10대 0.09배, 20대 0.75배). 가중치는 실제 매출 비중대로 작게 — 점수 기여가 아니라 저항 요인·코멘트 다양성 목적. 비중이 0에 가까운 연령대(10대 0.3%)는 가중치가 사실상 0이므로, **비율이 낮으면서 매출 비중이 3% 이상**인 층을 고른다.
- LLM은 각 세그먼트의 narrative 1~2문장만 생성. axes·weight·evidence는 코드가 채운다.

### 7.2 평가 프롬프트 구조 (페르소나 1콜)
```
[system] 너는 아래 특성의 손님이다. 광고를 보고 솔직하게 평가하라.
         부정적 평가를 주저하지 마라. 반드시 JSON 스키마로만 응답.
         evidence에는 제공된 피처의 path와 값을 그대로 인용하라 (새 수치 창작 금지).
[user]   ## 나의 특성: {persona.demo, axes, narrative}
         ## 우리 동네 데이터: {TradeAreaFeatures 관련 필드만}
         ## 광고물: {store.industry_label, brief.product/price/situation/tone, headline, sub}
         ## 평가 항목: attention/message/intent (0~100), resistance, comment
```

### 7.3 재생성 연결 (R7)
- 패널 모듈은 재생성 프롬프트를 만들지 않는다. `suggestions`(사장님 언어 2~3문장)와 `top_resistance`를 그대로 넘긴다.
- 우리 책임은 **"카피에 바로 반영 가능한 구체적 문장"으로 쓰는 것**까지 (예: "가격을 낮추기보다 '런치 세트 8,900원'처럼 묶음가로 제시"). 프롬프트에 어떻게 넣을지는 기본 파이프라인 설계.

## 8. 신뢰성 파이프라인 (R5 — 기술 코어, 의사코드)

```python
async def evaluate(ad, panel):
    evals = await gather(*[call_llm(p, ad) for p in panel.personas])   # 병렬 ≤20
    valid = []
    for p, e in zip(panel.personas, evals):
        if not schema_ok(e):                       # ① Pydantic 검증
            e = await retry_once(p, ad)
            if not schema_ok(e): exclude(p); continue
        if not evidence_match(e, panel.features):  # ② 근거 대조
            e = await retry_once(p, ad)
            if not evidence_match(e, panel.features): exclude(p); continue
        valid.append((p, e))
    scores = weighted_mean(valid)                  # ③ 가중 집계 (제외분은 가중치 재정규화)
    conf = "low" if weighted_std(valid) > SIGMA_MAX else "ok"   # ④ 분산 체크
    return EvaluationResult(..., excluded_cnt=len(panel)-len(valid))
```

- 원칙: **정량(세그먼트·가중치·집계·검증)은 전부 결정적 코드, LLM은 서사·평가 생성만.** 신뢰 판단의 근거는 모델의 자기보고가 아니라 코드 검증 결과다.
- 잔여 콜 예산은 유형 추가가 아니라 **동일 유형 반복 샘플링**에 쓴다 — 분산 체크의 통계 근거.
- SIGMA_MAX 초기값 20 (0~100 스케일), 운영하며 조정. 환경변수로.

## 9. 콜·비용 예산 (패널 모듈만 — 생성 비용은 별도)

| 작업 | 토큰/콜 (in/out) | 비용/회 추정 |
|---|---|---|
| 패널 구성 (서사 1콜) | 2k / 1.5k | ~$0.001 |
| 평가 1회 (≤20콜) | 1.5k / 0.3k × 20 | ~$0.01 |

- 평가 1,000회 ≈ $10 → 데모·시연에 충분. 초과 방어는 R9 한도(`EVAL_LIMIT`).
- 사용량은 event_log로 일 단위 집계 (SQL 1줄로 확인, 대시보드 없음).

## 10. 프론트 화면 명세 (모바일 375px 기준) — 패널 담당분만

| # | 화면 | 핵심 요소 | 요구사항 |
|---|---|---|---|
| S1 | 우리 동네 손님 미리보기 | 상위 페르소나 3개 카드 + 구성 차트 + 비중 조정 슬라이더. 챗봇이 주소를 받은 직후 노출 | R1 |

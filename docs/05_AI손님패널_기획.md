## 0. 범위

```
[건오·귀한] 챗봇 → 카피·이미지 생성 → 레이아웃 합성 ──> 완성된 광고물 ──┬──> 사용자에게 표시
                                                                          │
                            [아인·수호] ────────────────────────────────> └──> AI 손님 패널 평가
                                                                                    │
                                                        점수·저항요인·제안·코멘트 ───┘
                                                                └─(개선 제안 텍스트)─> 기본 파이프라인 재생성
```

| 우리가 만드는 것 | 우리가 만들지 않는 것 |
|---|---|
| 상권 데이터 파이프라인 (CSV→DuckDB, 주소→상권 피처) | 챗봇·NLU·슬롯 수집 |
| 패널 빌더 (페르소나 유형 + 인구 가중치) | 카피 생성, 이미지 생성, 레이아웃 합성 |
| 평가 엔진 (프롬프트·스키마·근거 검증·가중 집계) | 법령 준수 검사 (`compliance.py`) |
| 결과 화면 (지표·저항요인·제안·코멘트) | 재생성 실행 (개선 제안 텍스트만 전달) |
| 평가 사용량 로깅·한도 | 배포·인프라 (팀 공통) |

## 1. 개요

### 한 줄 정의
가게 주소의 상권 데이터로 그라운딩된 가상 손님 패널이, 기본 파이프라인이 만든 광고물을 **배포 전에** 평가해 점수·저항 요인·개선 제안을 돌려주는 평가 모듈.

### 형태
기본 파이프라인의 결과 화면에 붙는 평가 기능. 모바일 웹 우선(프론트 규약은 팀 결정을 따름).

### 배경
- 기본 파이프라인은 "광고물을 잘 만들어주는" 것까지다. 만들어진 광고물이 **그 동네 손님에게 먹히는지**는 아무도 답해주지 않는다.
- 기존 도구는 전부 "무엇을 파는가"(URL·제품사진) 관점. "누가 사러 오는가"(위치·상권) 관점 + 배포 전 검증 슬롯은 공백.
- 사장님의 진짜 페인은 "만들었는데 안 팔리면?"이라는 돈의 공포 → 만들어주기만 하는 도구와 달리, 만들고 **확인까지** 시켜준다.
- [01 타깃사용자 문서](01_타깃사용자_및_기능정의.md)의 "디지털 활용률은 높지만 83.3%가 기초·입문 단계"는 검증 기능에도 그대로 적용된다 — **결과 화면에 전문용어가 있으면 안 된다.**

## 2. 문제 · 해결

### 사용자 문제
- 광고·홍보물을 만들어도 **반응이 있을지 확인할 방법이 없다.** 배포하고 나서야 결과를 안다.
- 실패 비용은 사장님 몫: 인쇄비, 광고비, 그리고 "우리 동네엔 안 먹히는 메시지"로 날린 노출 기회.
- 디자인 도구(미리캔버스 등)는 만들게는 해주지만, 잘 만들었는지는 알려주지 않는다. 소비자 조사는 개인 사장님에게 비현실적.

### 해결 방안 (핵심 플로우)
1. **패널 구성**: 챗봇이 받은 가게 주소+업종 → 서울시 상권분석 데이터(연령·성별 매출 비중, 시간대 유동인구, 경쟁 밀도)로 그 동네 고객 구성을 반영한 **가상 손님 패널 자동 구성**. 타깃 비중은 수동 조정 가능.
2. **평가 요청**: 사용자가 완성된 광고물을 보고 "패널 평가받기" 버튼을 누른다. 평가 대상은 **사용자가 고른 시안 1개**.
3. **패널 평가**: 페르소나 유형 10~20개 × 인구 비중 가중치로 "수백 명 패널" 시뮬레이션. 평가 입력은 기본 파이프라인이 넘겨준 광고물 + 생성 컨텍스트(업종·규격·스타일·상품·문구·가격).
4. **결과**: 주목도·메시지 전달·방문/구매 의향 정량 지표 + 주 저항 요인 + 개선 제안 + 페르소나별 한 줄 코멘트.
5. **루프**: 개선 제안 텍스트를 기본 파이프라인에 넘겨 재생성 → 채택 시안은 로깅.

### 차별점
- **상권 그라운딩**: 아무 페르소나가 아니라 공공 상권 데이터에 근거한 "이 동네 실제 고객층". 근거 필드 필수로 환각 통제. 이게 빠지면 범용 평가기라 타협 불가.
- **정량은 코드, 정성만 LLM**: 세그먼트·가중치·집계·근거 대조는 전부 결정적 코드. LLM은 서사와 평가 문장만 쓴다 → "LLM에게 물어봤습니다"와 다른 재현성.
- **평가가 곧 생성 개선**: 평가 결과가 재생성 입력으로 들어가 루프가 닫힌다 → 서비스가 "만들어주는 도구"에서 "검증까지 되는 도구"가 된다.
- **데이터 자산**: 어떤 상권×업종에 어떤 광고가 채택되는가 로깅 → 재현 불가 데이터 축적.

## 3. 타깃 · 시나리오

### 제품 목표
서울의 요식업·카페 사장님이 만든 광고물에 대해, 버튼 한 번으로 30초 안에 "우리 동네 손님이 어떻게 볼지"를 근거와 함께 알려준다.

### 타깃 사용자
[01 타깃사용자 문서](01_타깃사용자_및_기능정의.md)와 동일. 검증 기능에서 특히 중요한 점:
- 광고물은 "감"으로 만들고 반응은 운에 맡기는 상태 → 근거 있는 피드백의 가치가 큼
- 전문 용어 없는 결과 화면 필수 (점수만 던지면 해석을 못 함)

### 사용자 시나리오 — 굵은 글씨가 우리 담당
1. 챗봇이 가게 주소·업종·상품을 받는다. → **"역삼동 이 상권은 30대 직장인 여성 매출 비중이 가장 높아요" 패널 미리보기**
2. 카피+이미지 시안이 생성된다.
3. 사장님이 마음에 드는 시안을 고르고 **"패널 평가받기"** 를 누른다.
4. **이 상권 가중치 기반 페르소나들의 평가**: 방문 의향 62% / 주 저항 요인: 가격 / "9,500원이면 옆집 샐러드랑 고민할 듯. '10분 컷'이라는 말엔 끌려요."
5. **"제안 반영해 다시 만들기"** → 개선 제안 텍스트가 기본 파이프라인으로 넘어간다 → 새 시안 → (원하면 다시 평가)
6. **채택 로깅** — 어떤 상권×업종에서 어떤 시안이 선택됐는지 기록

## 4. 지표 · 리스크

### 핵심 지표
- **활성화**: 시안 생성 → 평가 버튼 클릭률 (평가가 쓸모 있어 보이는가)
- **핵심 가치**: 재생성 루프 진입율 (평가 보고 수정 = 가치 체감 신호)
- **품질**: 근거 대조 탈락률(낮을수록 좋음), 분산 초과로 "신뢰도 낮음" 뜬 비율
- **자산 축적**: 채택 로그 건수 (상권×업종×시안 조합)

### 리스크
| 리스크 | 대응 |
|---|---|
| 평가 신뢰성 — "이게 진짜 손님 반응이야?" | 근거 필드 필수(어떤 상권 데이터 기반 판단인지 표기), JSON 스키마 강제, 근거↔실제 피처 대조 |
| 응답 편향 — 평가가 죄다 긍정/부정으로 쏠림 | 유형 다양성·부정 응답 허용 명시·집계 전 분산 체크 |
| 상권 데이터 한계 — 상권 추정치와 개별 가게 괴리 | "이 상권의 평균 고객층" 프레이밍, 분기 갱신 데이터 명시 |
| **데이터가 실시간이 아님** (최신 2026Q1, 약 2분기 지연) | **실측 결과 문제 없음** — 상권의 연령·성별 구성은 1년에 0.5~0.9%p, 5년에도 1.1~2.0%p만 변한다([06 §4.4⑥](06_기술계획서_품질검증.md)). 우리가 쓰는 축이 "동네 구조"라 느리게 변한다. 최신 트렌드·계절 이슈는 데이터가 아니라 평가하는 LLM이 커버 |
| **주소를 못 받음** (`context`에 `store_address` 미포함) | §6-1 합의 필요. 미합의 시 평가 화면에서 주소를 한 번 더 받는 폴백(UX 손해) |
| **업종 커버리지 불일치** (`industries.yaml`에 학원 등 비요식업) | 미지원 업종은 평가 버튼 비활성 + 안내. §6-6 합의 필요 |
| **인터페이스 표류** — 파이프라인 출력 형식이 개발 중 바뀜 | 계약을 Pydantic으로 고정하고 양쪽이 같은 스키마 파일 참조. 변경은 PR로 |
| API 비용 | 유형×가중치 설계로 평가 콜 캡(시안당 ≤20콜), 평가 횟수 한도, 사용량 로깅 |

## 5. 기본 속성

- **지역**: 서울 한정 — 경기 확장은 데이터 해상도 확인 후 결정(미결)
- **업종**: 요식업 + 카페·디저트 (그 외는 미지원 처리 — §6-6 합의 대기)
- **평가**: 파이프라인 출력물 1건. 페르소나 유형 10~20 × 인구 가중 집계, 시안당 ≤20콜, 30초 이내
- **데이터**: 서울시 상권분석서비스 CSV + 소진공 상가정보 → DuckDB 1회 적재, 카카오 로컬 API로 주소→행정동 변환
- **플랫폼**: 기본 파이프라인에 내장 (프론트·배포는 팀 규약을 따름)
- **가격**: 무료 (평가 횟수 제한)

## 6. 합의 필요 — 기본 파이프라인 담당자(건오·귀한)께

[03 기술계획서 §7-1](03_기술계획서_기본기능.md)의 체크박스 4개에 대한 답변과, 추가로 필요한 2건입니다.

| # | 항목 | 우리 제안 | 이유 |
|---|---|---|---|
| 1 | **`context`에 `store_address` 추가** | **필수** | 주소가 없으면 상권 매칭이 불가능해 이 기능의 존재 이유가 사라짐. 챗봇 슬롯에 이미 있는 값이라 전달만 해주시면 됨 |
| 2 | 검증 대상 | 사용자가 고른 시안 1개 | 3안 전부면 비용·시간 3배 |
| 3 | 실행 시점 | 버튼 클릭 | 자동이면 생성 시간에 얹혀 "1회 5분" 예산 초과 위험 |
| 4 | 응답 시간 예산 | 30초 이내 | 페르소나별 호출 병렬화, 시안당 ≤20콜 |
| 5 | 재생성 연결 | **예** | 개선 제안 텍스트를 넘기면 반영해 재생성하는 형태로 붙일 수 있을지 확인 부탁드립니다 |
| 6 | **미지원 업종 처리** | 평가 버튼 비활성 + 안내 문구 | `industries.yaml`에 학원 등이 있으나 상권 피처는 요식업·카페만 커버. "아직 이 업종은 동네 데이터가 없어요" 안내 |

### 왜 주소 말고 다른 정보는 안 받는가
페르소나 **구성**에는 주소 + 업종만 쓰고, 나머지(상품·스타일·규격·문구·가격)는 구성이 아니라 **평가 단계**에서 씁니다.

```
주소 + 업종        →  "이 동네 손님은 누구인가"       (페르소나 구성)
광고물 + 컨텍스트  →  "그 손님이 이걸 어떻게 보는가"   (평가)
```

광고 정보로 페르소나를 만들면 "이 광고에 반응할 만한 손님"을 만들어놓고 그 손님에게 평가받는 자기충족이 됩니다. 페르소나는 광고와 무관하게 동네 데이터만으로 결정돼야 평가가 의미를 갖습니다.

`format`(인스타/전단지/현수막)은 이미 `context`에 있지만 **일부러 쓰지 않습니다.** 채널마다 도달하는 사람이 다른 건 맞지만 서울시 상권 데이터에 채널별 도달 정보가 없어서, 보정하려면 계수를 지어내야 합니다. 근거 없는 숫자를 넣는 순간 "공공 데이터 기반"이라는 근거가 무너지므로, 보정하지 않고 결과 화면에 "오프라인 상권 데이터 기준"이라고 한계를 표기합니다. 영업시간도 같은 이유로 지금은 받지 않습니다(슬롯 추가 = 사장님 부담).

## 7. 담당 분담 (아인·수호)

경계는 `build_features(address, category) → TradeAreaFeatures` 하나.

- **이아인 — 데이터·패널**: CSV→DuckDB ETL, 주소→상권 매칭, 피처 함수, 페르소나 유형·가중치 생성
- **최수호 — 평가·집계**: 평가 프롬프트·스키마, 병렬 호출, 근거 검증, 가중 집계, 결과 화면

피처 스키마와 `Persona` 스키마를 **D1에 먼저 고정**하면 둘을 병렬로 진행할 수 있습니다. 평가 쪽은 데이터 쪽 산출을 기다리지 않고 하드코딩 픽스처(`tests/panel/fixtures/features_역삼.json`)로 시작합니다.

## 0. 광고 완성 계약 — 이 백엔드를 붙이는 전제

**GPT 결과는 완성 광고가 아니라 "글자 없는 사진 재료"다.** 이 전제가 깨지면 서비스가
광고 제작기가 아니라 사진 보정기가 된다. 이미지 백엔드는 아래 계약 위에서만 의미가 있다.

| # | 계약 | 현재 | 이 백엔드가 지켜야 할 것 |
|---|---|---|---|
| 1 | 백엔드 결과는 **반드시 compose_ad/generate_poster 를 거친다** | ✅ | 백엔드가 최종 이미지를 직접 반환하지 않는다 |
| 2 | 이미지에 얹는 문구는 **사장님이 선택한 것** (패널은 추천·정렬을 도울 뿐, 자동 선택이 아니다) | ❌ `copies[0]` 자동 사용 (app.py) | 백엔드는 문구를 모른다 — 선택 결과를 받는 구조가 선행돼야 함 |
| 3 | 사진이 있으면 **상품 보존**, 없을 때만 새 장면 생성 | 🟡 `generate` 갈래가 사진이 있어도 새로 그림 | **확정: 사진이 있으면 전체 생성 금지** — 편집 또는 원본 유지로만 |
| 4 | 결과에 **다시 만들기** 가 있어야 한다 | ❌ 이미지 경로에 없음 (문구 경로에는 있음) | 재생성 시 백엔드를 다시 부르는 비용·시간 고려 |
| 5 | 결과를 **저장·다운로드** 할 수 있어야 한다 | ❌ | 백엔드 밖 과제이나, 이 연결 없이는 "광고를 만들었다"가 성립하지 않음 |
| 6 | 근거 없는 정보를 광고에 넣지 않는다 | 🟡 `poster_plan` 이 업종 통념으로 특징을 추론 | 백엔드와 별개 과제 — 광고 정확성 |

**따라서 이 백엔드의 우선순위는 뒤쪽이다.** 순서:

```
완료         poster_plan 지어내기 방지 — 광고 정확성 (PR #23, 2026-08-16)
대기         PR #21·#22·#23 리뷰·머지
그다음       광고 완성 흐름 연결 (문구 선택 → 이미지 → 재생성 → 저장·다운로드)
그다음       이미지 백엔드 (이 문서)
그다음       4:5 우선 지원 · 정보 포스터 실험(정육·헬스장 등)
```

완성 흐름 없이 엔진만 좋아지면 "세로로 긴 예쁜 사진"이 나올 뿐이다.

## 1. 현재 구조

```
사장님 주문(AdBrief) + 사진(선택)
        │
        ├─ 사진 있음 ─→ remove_background(누끼) ─→ route_photo(청소 전 누끼)
        │                    ├ keep     원본을 배경으로
        │                    ├ cutout   청소된 누끼 + sd-turbo 생성 배경
        │                    └ generate sd-turbo 로 제품이 든 장면 통생성
        └─ 사진 없음 ─→ sd-turbo hero 생성

버튼 한 번 = 두 형태를 각각 생성 (app.py `_make_images`)
   simple(감성 피드형) → compose_ad(배경 사진 + 문구)
   poster(정보 포스터형) → generate_poster(**제품 누끼 RGBA** + 기획 텍스트)
```

| 부품 | 역할 | 모델 |
|---|---|---|
| `photo_router.route_photo` | 갈래 판정 | gpt-4o-mini (비전) |
| `prompt_builder` | 한→영 프롬프트 | gpt-4o-mini |
| `poster_plan.plan_poster` | 포스터 기획(태그라인·특징) | gpt-4o-mini |
| `gen_background.generate_background` | 이미지 생성 | **sd-turbo (2스텝, 로컬 GPU)** |
| `background.remove_background` | 누끼 | rembg (로컬 CPU) |
| `compose.compose_ad` / `poster.generate_poster` | 문구 조판 | 코드 |

**실험에서 드러난 한계**: 사진 없는 주문은 주문과 다른 결과(아이스→핫 3잔) · cutout 은 누끼 경계가 거칠고 합성 흔적 · 다제품 상품 소실은 **PR #22 로 해결됨**.

## 2. 제안 구조 (hybrid)

> **A단계 구현 결정 (2026-08-20):** 현재 구현은 프로필을 `local | openai`
> 두 개로 시작한다. `openai`는 GPT 생성이 실패하면 로컬로 폴백하고 화면에
> 안내하므로, 아래 전체 설계의 `hybrid` 동작을 우선 겸한다.
>
> 아래의 `openai | hybrid` 분리, 재시도, 호출 상한은 후속 범위다.
> 폴백 안내를 담는 `_notices`는 현재 프로세스 전역이므로 단일 사용자 시험까지만
> 허용하며, 여러 사용자가 접속하는 배포 전에는 세션별 전달 방식으로 바꿔야 한다.
>
> 이번 A단계는 **원본 사진을 GPT에 전달하지 않는 생성 경로만 연결한다.**
> 사진이 없거나 `generate` 갈래면 상품이 포함된 장면을 생성하고, `cutout` 갈래면
> 누끼 뒤에 놓을 배경을 생성한다. `keep`·포스터형·스케치 갈래는 GPT를 호출하지 않는다.
> 원본 사진 자체를 GPT로 보정하는 `edit_photo`는 B단계이며 토요일 기능 동결 전
> 완료해야 한다. 따라서 A단계만으로 전체 GPT 이미지 백엔드가 완성된 것은 아니다.
>
> **B단계 구현 결정 (2026-08-21):** `openai` 프로필의 감성형에서 사진 라우터가
> `cutout` 또는 `generate`로 판정한 실제 사진은 `gpt-image-2` 편집으로 정돈한다.
> `keep`은 계속 API 0콜이며, 편집 실패 시 상품 보호를 위해 로컬 누끼 경로가 아니라
> 원본 사진으로 폴백하고 화면 안내를 남긴다. 실제 상품을 보존한 편집이므로
> `staged=False`를 유지한다. 사진과 스케치가 함께 있으면 스케치의 구도 계약을
> 조용히 버리지 않도록 이번 B단계 편집에서 제외하고 기존 누끼·스케치 합성을 쓴다.
> 포스터형과 `local` 프로필은 변화가 없다.

핵심: **`gen_background` 한 부품을 갈아끼우는 게 아니라, 그 위에 이미지 백엔드 계층을 둔다.**
GPT 편집은 "원본 사진 + 주문 → 사진 전체 재연출"이라 "프롬프트 → 빈 배경"과 역할이 다르기 때문.

```
                    IMAGE_PROFILE = local | openai | hybrid     (기본값 local)
                                  │
        ┌─────────────────────────┴─────────────────────────┐
        │                이미지 백엔드                        │
        │  edit_photo(photo, brief, size) -> (Image, Meta)   │  ← 사진 있음
        │  generate_scene(brief, size)   -> (Image, Meta)    │  ← 사진 없음
        └─────────────────────────┬─────────────────────────┘
                                  ↓
                       compose_ad (감성 피드형에만)
```

| 프로필 | edit_photo | generate_scene | 용도 |
|---|---|---|---|
| `local` **(기본값)** | 누끼 + sd-turbo 배경 합성 (현행) | sd-turbo hero (현행) | 무료·오프라인·CI·기본 개발 |
| `openai` | gpt-image-2 편집 | gpt-image-2 생성 | 품질 우선, 폴백 없음(설정 오류는 명시) |
| `hybrid` | gpt-image-2 → 실패 시 폴백 | gpt-image-2 → 실패 시 로컬 hero | 데모·발표 환경에서 **명시적으로 선택** |

> **기본값을 `local` 로 두는 이유**: `.env` 에 OpenAI 키를 넣어둔 팀원이 이미지 버튼을 눌렀다가
> 의도치 않게 과금될 수 있습니다. PR #18 에서 "stub 인데 이미지만 실제 API 를 부르던" 문제를
> 막았는데 같은 사고를 반복하지 않기 위해서입니다. 데모 환경에서만 `hybrid` 를 명시합니다.

**갈래 판정(`route_photo`)은 그대로 유지**합니다 — "원본이 이미 좋으면 그대로(keep)"가 가장 안전·빠름·무료.
즉 **"GPT 가 모든 사진을 보정"하는 구조가 아니라, "라우터가 보정이 필요하다고 판단한 사진에만 GPT 를 쓰는" 구조**입니다.
[추측] keep 판정 기준은 GPT 도입 후 재조정이 필요할 수 있습니다.

## 3. 두 형태(감성/포스터) 처리 — v0.1 에서 빠졌던 부분

**문제**: `generate_poster` 는 완성 사진이 아니라 **제품 누끼(RGBA)** 를 받습니다. GPT 편집 결과는
배경까지 완성된 RGB 사진이라 포스터에 그대로 넣을 수 없습니다.

**제안 (v1 범위)**

| 형태 | 처리 | API 콜 |
|---|---|---|
| 감성 피드형 (simple) | **GPT 편집/생성 적용** → compose_ad 로 문구 | 이미지 API **1콜** |
| 정보 포스터형 (poster) | **기존 방식 유지** — 원본 누끼(사진 있음) 또는 로컬 hero(사진 없음) | 이미지 API **0콜** |

**버튼 한 번당 호출·시간·비용 [추측 — 실험값 기반 계산]**

| 주문 | 이미지 API | 텍스트 LLM | 예상 시간 | 예상 비용 |
|---|---|---|---|---|
| 사진 있음 | 편집 1콜 | 갈래 판정 1 + 포스터 기획 1 | 감성 50~60초 + 포스터 5~10초 | 약 90원 + 텍스트 1원 미만 |
| 사진 없음 | 생성 1콜 | 프롬프트 1 + 포스터 기획 1 | 감성 45~55초 + 포스터 7~15초 | 약 74원 + 텍스트 1원 미만 |

**"두 형태가 GPT 결과를 공유할 수 있나"** → v1 에서는 **공유하지 않습니다.**
[추측] GPT 편집 결과를 다시 rembg 로 누끼 따서 포스터 제품으로 쓰는 방법은 가능해 보이지만,
①편집 결과의 제품 형태가 원본과 미세하게 다를 수 있고 ②누끼 품질을 재검증해야 해서 v1 범위 밖으로 둡니다.
→ **미결 §7-2**

## 4. 흐름 (정상 / 실패)

### 4-1. 사진 있는 주문 (감성 피드형)

```
사진 → 누끼 → route_photo
   ├ keep     → (이미지 API 안 부름) 원본 + compose        ← 지금과 동일, 무료
   ├ cutout   → edit_photo(원본 사진, brief)               ← GPT 편집  ★변경점
   └ generate → edit_photo 또는 원본 유지 (§7-2)           ← ⚠️ 전체 생성 금지: 사진이 있으면
                                                             상품을 새로 그리지 않는다 (§0-3)
```

**실패 시**
```
edit_photo 실패
   → §5 조건에 해당하면 재시도 1회
   → 폴백: 원본 사진을 그대로 배경으로 + compose (= keep 과 같은 결과)
   → 안내: "사진 보정에 실패해 원본으로 만들었습니다"
```
⚠️ **로컬 cutout·generate 로 내려가지 않습니다.** 그쪽은 상품을 오리거나 새로 그려서 상품이 손상될 수
있고, 그럴 바엔 원본이 안전합니다 (PR #22 와 같은 원칙).

### 4-2. 사진 없는 주문 (감성 피드형)

```
주문만 → generate_scene(brief)     ← GPT 전체 생성  ★변경점
실패 → 재시도(조건부) → 로컬 hero(sd-turbo)
   → 안내: "고품질 생성에 실패해 기본 생성으로 만들었습니다"
```
사진이 없을 땐 원본이라는 안전망이 없으므로 로컬 생성이 유일한 대안입니다.

### 4-3. 포스터형

이미지 API 를 쓰지 않으므로 현행과 동일합니다. 실패 처리도 현행 유지.

## 5. 오류·재시도·키 부재

### 5-1. 재시도 (모든 오류에 적용하지 않음)

| 오류 | 재시도 | 근거 |
|---|---|---|
| `429`(요청 과다) · `5xx`(서버) | **1회** | 일시적 오류 |
| 콘텐츠 정책 거부 | ❌ | 같은 입력이면 같은 결과 |
| 잘못된 요청(4xx, 파라미터·이미지 형식) | ❌ | 재시도해도 실패 |
| 인증 실패 | ❌ | 설정 문제 (§5-2) |
| **읽기 타임아웃** | **미결 §7-6** | 서버에서 이미 생성·과금됐을 수 있음 → 우선 **폴백**, 자동 재시도는 팀 결정 |

### 5-2. API 키가 없을 때

| 프로필 | 처리 |
|---|---|
| `local` | 정상 — 애초에 API 를 쓰지 않음 |
| `hybrid` | 로컬 폴백 + 화면 안내 + 로그 1줄 ("키가 없어 기본 생성으로 만들었습니다") |
| `openai` | **설정 오류로 명확히 안내** — 조용히 로컬로 내려가지 않음 (프로필과 실제 동작이 달라지면 안 됨) |

### 5-3. 예외 변환

app.py 의 기존 예외 그물(`OSError·ValueError·RuntimeError·ImportError`)을 그대로 쓰려면 백엔드가
외부 예외를 내부 예외로 변환해야 합니다 (#18 에서 세운 원칙과 동일).

## 6. 규격 (크기·비율)

| 값 | 비율 | 비고 |
|---|---|---|
| `1024×1024` | 1:1 | 실험에서 사용. 현재 compose 기본과 같은 비율 |
| `1024×1536` | **2:3** | ⚠️ v0.1 에서 "4:5" 라고 잘못 적었음 |
| `1024×1280` | **4:5** | 인스타 피드 **권장** 비율. [추측] 공식 제약(변 ≤3840, 16 배수, 비율 ≤3:1, 총 픽셀 65만~830만)을 만족하므로 가능해 보이나 **실호출로 확인 필요** |

**변환 경로 [추측]**: GPT `1024×1280` → compose 출력 `1080×1350` (둘 다 4:5라 비율 왜곡 없이 확대).
단 compose v2 의 안전 영역·글자 크기는 정사각 기준으로 실측했으므로 4:5 에서 재확인이 필요합니다 (→ 미결 §7-4).

⚠️ **1:1 은 폐기된 규격이 아닙니다.** 인스타는 여전히 넓은 비율 범위를 지원하고 광고 권장은 1:1 또는 4:5 입니다.
따라서 목표는 "4:5 **강제**"가 아니라 **"4:5 우선 지원, 1:1 유지"** 입니다.
또한 팀 문서(docs/01)의 "이미지 위 텍스트 20% 초과 시 도달 50% 감소·3일 만에 게재 중단"은
**현재 공식 근거를 확인하지 못했습니다.** 고정 차단 규칙으로 구현하지 않고, 필요해지면
"글자가 많아 보일 수 있어요" 수준의 디자인 경고로만 검토합니다 (→ §11).

## 10. 필요한 자동 테스트 (전부 대역, 실제 API 호출 없음)

**CI 에는 OpenAI 키가 없으므로 실제 호출이 있으면 안 됩니다.**

| # | 고정할 계약 |
|---|---|
| 1 | `IMAGE_PROFILE=local`(기본값) 이면 API 클라이언트를 만들지 않는다 |
| 2 | `hybrid` + 편집 성공 → 편집 결과가 compose 로 전달된다 |
| 3 | `hybrid` + 편집 실패 → **원본 사진**이 배경으로 쓰인다 (로컬 cutout 으로 내려가지 않는다) |
| 4 | `hybrid` + 생성 실패 → 로컬 hero 가 쓰인다 |
| 5 | `429`·`5xx` 는 **1회만** 재시도한다 (총 2회 호출) |
| 6 | 정책 거부·4xx 는 재시도하지 않고 즉시 폴백한다 |
| 7 | `hybrid` + 키 없음 → 로컬 폴백 + 안내 플래그 |
| 8 | `openai` + 키 없음 → 설정 오류를 명확히 알린다 (조용한 폴백 금지) |
| 9 | 호출 상한 도달 시 API 를 아예 호출하지 않는다 |
| 10 | 폴백이 일어나면 안내 플래그(Meta)가 화면까지 전달된다 |
| 11 | 실행 기록(모델·시간·request id·usage)이 남는다 |
| 12 | keep 갈래는 프로필과 무관하게 이미지 API 를 부르지 않는다 |
| 13 | 포스터형 경로는 이미지 API 를 부르지 않는다 |

## 11. 후속 과제 (이번 PR 범위 밖)

- 패널 평가와 이미지 생성 **병렬 실행** — 현재 화면 흐름과 얽혀 별도 설계 필요
- 로고·포장 글자 보존 시험
- GPT 결과를 포스터형과 공유(누끼 재추출)
- 4:5 **우선 지원** 시 compose v2 안전영역 재실측 (1:1 도 계속 지원)
- 글자 밀도 **경고**(차단 아님) — 근거를 다시 확인한 뒤에만
- 화이트밸런스 자동 보정 — GPT 편집이 조명·색감을 정돈하면 중복일 수 있어 백엔드 결정 후 판단
- `poster_plan` 의 근거 없는 특징 추론 방지 (광고 정확성 — 백엔드와 별개 과제)
- 패널이 이미지까지 평가하도록 확장 (현재 패널은 문구만 봄)
- `ref_id`·`sketch_id` 실제 사용 (현재 저장만 되고 생성에 쓰이지 않음)
- 실제 운영·외부 배포 시 **별도 운영 계정·결제수단·키, 사용자별 생성 횟수와 월 한도** — 배포 채널과 시점은 팀 결정

## 3. 사용자 흐름 — 챗봇

### 3-1. 왜 챗봇인가

폼 방식은 한 화면에 업종·사진·규격·스타일·상품명·가격이 전부 보인다.
**기초·입문 단계가 83.3%인 사용자에게는 선택지가 한꺼번에 보이는 것 자체가 부담**이다.

### 3-2. 전체 구조

```
[대화] ──> 슬롯 수집 ──┬──> ① 이미지 파이프라인 ──┐
                      │                          ├──> ③ 레이아웃 합성 ──> PNG
                      └──> ② 문구 파이프라인 ────┘
                                                  └──> ④ 법령 근거 제시
```

`src/` 는 Streamlit 에 의존하지 않는다. **프론트를 바꿔도 도메인 로직은 재사용된다.**

앞쪽 **"슬롯 수집"이 4장**, 뒤쪽 **생성이 5장**이다.

## 4. 정보 수집 설계 — 자연어와 선택지를 한 화면에

> 이 장이 이번 설계의 핵심이다. **무엇을 받아야 하고, 어떻게 받을 것인가.**

### 4-1. 핵심 원칙 — 경로를 고르게 하지 않는다

초안에서는 첫 화면에 *"말로 하시겠어요, 골라서 하시겠어요?"* 를 물었다.
**그 질문 자체가 사용자에게 부담**이라 없앴다.

대신 **매 질문마다 선택지와 자유 입력을 함께 제시**한다.
실무에서 **mixed-initiative(혼합 주도)** 라 부르는 방식이다.

```
🤖 어떤 가게를 하고 계세요?

   [☕ 카페] [🍚 음식점] [🥩 정육점] [💇 미용실] …
   ┌──────────────────────────────────────────┐
   │ 말로 하셔도 돼요                           │
   └──────────────────────────────────────────┘
```

| 얻는 것 |
|---|
| **선택지가 곧 힌트** — 빈 입력창 앞에서 막히지 않는다. 뭘 물어보는지 보고 말로 풀어 쓴다 |
| **경로 선택이라는 결정이 사라진다** |
| **중간 전환이 자연스럽다** — 3번째까진 말로, 4번째는 클릭 |

### 4-2. 무엇을 채우는가 — 슬롯 정의

슬롯마다 **어느 층인지**와 **필수 여부**를 정한다.
이게 없으면 "언제 생성 가능한가"를 판단할 수 없다.

| 슬롯 | 층 | 필수 | 값의 형태 | 자연어로 채움 |
|---|---|:---:|---|:---:|
| `industry` | 프로필 | ✅ | 레지스트리 id (`cafe`) | ✅ |
| `name` | 프로필 | — | 자유 문자열 | ✅ |
| `phone` `address` | 프로필 | — | 자유 문자열 | ✅ |
| `goal` | 작업 | ✅ | `copy` / `image` | ✅ |
| `format` | 작업 | ✅ | 레지스트리 id | ✅ |
| `style` | 작업 | ✅ | 레지스트리 id | ✅ |
| `product` | 작업 | ✅ | 자유 문자열 | ✅ |
| `photo` `sketch` `reference` | 작업 | — | 파일 | ❌ **말로 못 채움** |
| `items` (가격·조건) | 작업 | — | `[{name, price}]` | ❌ **AI 가 생성 금지** |
| `request` | 작업 | — | 자유 문자열 | ✅ |

**필수 5개가 다 차면 생성 가능**하다. 두 경로의 공통 종료 조건이다.

#### 층을 나누는 이유

| 층 | 성격 | 예 |
|---|---|---|
| **가게 프로필** | 매번 같다. **저장해서 재사용** | 업종 · 상호 · 연락처 |
| **이번 작업** | 매번 다르다 | 무엇을 · 어디에 · 어떤 느낌 |

동네 매장의 실제 사용 패턴이 **매주 반복**이다. 매주 업종과 전화번호를 다시 묻게 하면 안 된다.

> **판단 기준**: "매번 똑같고, 결과물에 실제로 들어가는가"
> 이 기준을 못 넘으면 프로필에 넣지 않는다.
> 사장님의 나이·성별 같은 정보는 **생성에 쓰이지 않으므로 받지 않는다.**

#### 한 문장에 두 층이 섞여 들어온다

```
"난 카페 사장이고  크로플 사진을 만들건데  가격을 추가하고  감성적으로 하고싶어"
   └─ 프로필 ─┘   └───── 작업 ─────┘  └── 작업 ──┘  └── 작업 ──┘
```

그래서 NLU 출력을 **프로필 / 작업 두 바구니로 분류**하는 단계가 필요하다.

### 4-3. 자유 입력이 들어왔을 때

```
입력 → ① 선택지 매칭 → ② NLU 추출 → ③ 정규화 → ④ 검증 → ⑤ 분류 → ⑥ 인라인 확인
```

#### ① 선택지 먼저 매칭 — 비용 절감

사용자가 `"카페요"`, `"없어요"` 처럼 **현재 질문에 짧게 답하는 경우**가 많다.
이때 LLM 을 부르는 것은 낭비다. **현재 노드의 선택지와 먼저 대조**하고, 실패할 때만 NLU 로 넘긴다.

> 버튼 클릭은 당연히 NLU 를 거치지 않는다.

#### ② NLU 추출

LLM 에 **structured output** 으로 스키마를 강제한다.

```
출력:  { slot: { value, evidence } | null }
```

**두 가지를 반드시 강제한다.**

| 규칙 | 이유 |
|---|---|
| 못 알아들은 슬롯은 **null** | 억지로 채우면 사장님이 말하지 않은 조건이 광고에 들어간다 |
| `evidence` — 어느 표현에서 뽑았는지 | 확인 화면에서 사용자가 오인식을 잡을 수 있게 |

#### ③ 정규화 — 가장 어려운 지점

LLM 은 `"카페"` 라고 답하는데 레지스트리 id 는 `cafe` 다.

| 방법 | 평가 |
|---|---|
| ① LLM 에 **id 목록을 주고 그중 하나로** 답하게 (enum 강제) | **권장.** 매핑 단계가 사라진다 |
| ② 자유롭게 받고 후처리 매핑 | 실패 케이스를 계속 메꿔야 한다 |

①을 쓰되 **enum 목록을 레지스트리에서 동적으로 생성**해야 한다.
업종을 추가했는데 프롬프트가 그대로면 새 업종을 영영 못 뽑는다.

> **애매한 입력은 null 이 정답이다.**
> `"인스타"` 만으로는 피드인지 스토리인지 모른다. 찍게 하지 말고 **비워서 되묻는다.**

#### ④ 검증

LLM 이 목록에 없는 id 를 반환할 수 있다(환각).
**레지스트리에 실제로 있는지 확인하고, 없으면 버린다.**

#### ⑤ 분류

프로필 슬롯과 작업 슬롯으로 나눈다. 프로필 쪽은 **저장 후보**가 된다.

#### ⑥ 인라인 확인

별도 확인 화면을 두지 않는다. **말풍선 안에서 한 줄로** 처리한다.

```
🤖 ✅ 카페·디저트 · 크로플 · 인스타 피드 · 이미지 — 이렇게 이해했어요  [수정]

   어떤 느낌으로 만들까요?
   [🕯️ 따뜻] [◻️ 모던] [🔥 특가] [🌿 신선]
```

**`[수정]` 은 필수다.** 한 문장으로 4개가 차면 틀린 것도 4개일 수 있다.
전부 거부하고 처음부터 하는 것 말고 **그 슬롯만 고치는 경로**가 있어야 한다.

#### 값 없는 요청 처리

`"가격을 추가하고"` 는 **필요하다는 신호지만 값이 없다.**
그리고 **가격은 AI 가 지어내면 안 되는 값**이다.

```
items_requested: true    ← 신호
items: []                ← 값은 비어 있음
```

→ 되묻기에서 **우선순위가 올라간다.**

### 4-4. 되묻기 규칙

| 규칙 | 내용 |
|---|---|
| 무엇을 물을까 | 비어 있는 **필수 슬롯**만 |
| 순서 | `flow.yaml` 의 노드 순서 그대로 — 별도 우선순위 로직 불필요 |
| 파일은 항상 물음 | 사진·스케치·레퍼런스는 말로 못 채운다 |
| 선택 슬롯 | 안 물어본다. 단 `_requested` 신호가 있으면 물어본다 |
| 조건부 프로필 | 연락처·주소는 **전단지·POP 규격일 때만.** 인스타 피드엔 필요 없다 |

### 4-5. 대화 흐름은 데이터로 둔다

질문 순서를 `if/elif` 로 짜면 순서 변경·질문 추가가 불가능해진다.

```yaml
- id: ask_format
  kind: choice
  ask: 어디에 쓰실 건가요?
  decides: 캔버스 크기 · 글자수 상한 · 옥외광고물법 적용 여부
  store: format
  nl_fillable: true       # 자연어에서 채웠으면 이 질문을 건너뛴다
  source: formats         # 선택지를 레지스트리에서 자동 생성
  next: ask_style
```

- `source: formats` — 규격을 추가해도 flow.yaml 을 고칠 필요가 없다
- **되돌아가기**는 답변 직전 상태의 스냅샷을 저장해 복원한다 (역방향 계산 불필요)

### 4-6. 프로필 저장 — 단계별

**로그인을 먼저 띄우지 않는다.** 가치를 보기 전에 가입하지 않는다.

```
앱 시작 → 바로 대화 → 결과물 확인 → "다음에도 쓰시게 저장할까요?"
```

| 단계 | 저장 | 로그인 |
|:---:|---|---|
| 1 | **로컬 JSON** (`data/`, gitignore) | 없음. 화면에 로그인 개념 자체가 없다 |
| 2 | 프로필 여러 개 | 없음. 선택만 |
| 3 | DB | 이때 도입. 게스트 프로필 **이전 처리 필요** |

저장소는 인터페이스로 추상화해 **1단계 → 3단계가 구현 교체로 끝나게** 한다.

```python
class ProfileStore(Protocol):
    def load(self, key) -> StoreProfile | None: ...
    def save(self, key, profile) -> None: ...
```

> 로그인은 프로젝트 평가 항목(정확도·일관성·응답속도·UI·완성도·제어가능성)에
> 직접 걸리지 않는다. **3단계는 "여유 되면"으로 둔다.**

### 4-7. 결정이 필요한 것

- [ ] **자유 입력이 이미 채운 슬롯을 덮어쓸까?** `"아니 스토리로"` 는 덮어써야 하지만, 실수로 덮어쓰는 것도 막아야 한다
- [ ] **선택지를 몇 개까지 보여줄까?** 업종 7개를 다 보여줄지, 자주 쓰는 것만 보이고 접을지 (모바일 공간)
- [ ] **파일 업로드 단계에서도 자유 입력을 열어둘까?**
- [ ] **자연어를 아무것도 못 알아들었을 때** 조용히 선택형으로 갈지, 물어볼지
- [ ] **저장 제안 시점** — 결과물 직후 / 다운로드 시 / 연락처가 처음 필요할 때

## 5. 생성 파이프라인

### 5-1. 이미지 파이프라인 — 모드 6종

**사용자는 모드를 고르지 않는다. 무엇을 올렸는지로 자동 결정된다.**

입력은 세 가지다 — **제품 사진 / 스케치 / 레퍼런스**.

| 제품 사진 | 스케치 | 레퍼런스 | 모드 | 기법 | 요구사항 |
|:---:|:---:|:---:|---|---|---|
| ✓ | — | ✗ | `preserve` | 누끼 + Inpainting (배경만 교체) | 이미지 3 |
| ✓ | — | ✓ | `preserve_ref` | 위 + IP-Adapter | 이미지 2+3 |
| ✗ | ✓ | ✗ | `sketch` | **ControlNet (scribble)** | **이미지 4** |
| ✗ | ✓ | ✓ | `sketch_ref` | ControlNet + IP-Adapter | 이미지 2+4 |
| ✗ | ✗ | ✓ | `reference` | t2i + IP-Adapter | 이미지 2 |
| ✗ | ✗ | ✗ | `scene` | t2i (글자 얹을 배경만) | 이미지 1 |

**여섯 모드가 같은 base 모델 위에서 conditioning 만 다르다.**
Inpainting / ControlNet / IP-Adapter / 순수 t2i 의 조합이므로 **모델은 한 번만 올린다.**

> **제품 픽셀 보존이 원칙이다.** 법적 이유(표시광고법)뿐 아니라
> 실물과 다르면 리뷰 불만·반품으로 돌아온다는 실무적 이유도 있다.
> → **보정 강도에 상한**을 둔다.
>
>  **스케치 모드는 이 원칙의 예외다.** 실제 제품 사진이 없으므로 보존할 픽셀이 없다.
> 대신 **실존 제품을 사칭하지 않는 용도**(배경·분위기·컨셉 연출)로 한정한다.
> "이 그림이 실제 우리 제품입니다"로 쓰이면 허위광고가 된다.

### 5-1-1. 스케치 입력을 챗봇 흐름에 넣기

기존 "제품 사진 있으세요?" 질문을 **3지선다로 확장**한다.

```
⑤ 제품 사진이 있으신가요?
   [📷 사진 있어요]  [✏️ 직접 그려볼게요]  [없어요]
        │                   │                  │
     업로드           캔버스로 스케치        건너뜀
```

`configs/flow.yaml` 의 노드 하나를 고치고 `kind: canvas` 를 추가하면 된다.
**대화 흐름이 데이터로 분리돼 있어 코드 변경이 최소화된다** (4-5 설계의 이득).

### 5-2. 문구 파이프라인

```
사진 ──> VLM 캡션 ──┐
업종 페르소나 ───────┼──> 금칙 규칙 주입 ──> LLM ──> 헤드라인·서브카피 3안
스타일 어조 ─────────┤
규격 글자수 상한 ────┘
```

- **가격은 LLM 이 생성하지 않는다.** 사장님이 입력한 값만 쓴다 (환각 = 표시광고법 위반)
- 금칙 규칙은 **프롬프트에 주입**해 애초에 위반 문구가 안 나오게 한다 ([02 문서](02_광고규제_준수기능_설계.md))

### 5-3. 레이아웃 합성

**Diffusion 모델은 한글을 제대로 그리지 못한다.**
이미지는 "글자 없는 배경"으로만 만들고 한글은 PIL 로 얹는다.

- 배치 패턴 4종(`bottom_band` / `top_bottom` / `side_panel` / `list_grid`)을 규격들이 공유
- 덤으로 **문구만 수정하면 GPU 재실행 없이 즉시 재출력**된다

### 5-4. 3축 직교 레지스트리

업종 N × 스타일 M × 규격 K 를 전부 만들면 조합 폭발이지만,
세 축이 **독립적인 역할만** 담당하면 정의는 `N + M + K` 개로 끝난다.
업종 추가 = YAML 10줄. **코드에 하드코딩된 업종 목록이 없다.**

## 7. 확장 지점 — 팀원 기능이 붙는 자리

> 세 명이 각자 계획서를 쓰지만 **서비스는 하나**다. 여기서 경계를 정의한다.
> **아래 '결정 필요' 항목은 담당자와 합의가 필요하다.**

### 7-1. 광고 품질 검증 (AI 페르소나) — 담당: 팀원

**붙는 위치**: 결과 화면. 기본 파이프라인의 **출력을 입력으로 받는다.**

```
[레이아웃 합성] ──> 완성된 광고물 ──┬──> 사용자에게 표시
                                    └──> 품질 검증 ──> 점수 + 피드백
```

**제안 인터페이스**

```python
evaluate(
    image,                 # 최종 PNG
    headline, sub, items,  # 문구·가격
    context,               # industry / format / style / product / mode
) -> 점수 + 항목별 피드백
```

내가 보장할 것: **결과물과 함께 생성 컨텍스트를 전달**한다.
업종·규격을 모르면 "이 광고가 적절한가"를 판단할 수 없기 때문이다.

**결정 필요 (담당자와 합의)**

- [ ] 검증 대상 — **3안 전부**인가, **사용자가 고른 1개**인가
- [ ] 실행 시점 — **자동**인가, **버튼 클릭**인가 (자동이면 생성 시간에 더해진다)
- [ ] 응답 시간 예산 — 2장 목표 "1회 5분 이내" 안에 들어와야 한다
- [ ] 피드백을 받은 뒤 **재생성으로 연결**할 것인가

### 7-2. 옷 사진 → 착용 모델 생성 — 담당: 팀원

**붙는 위치**: 이미지 파이프라인. **기존 모드와 겹치므로 정리가 필요하다.**

**결정 필요 (담당자와 합의)**

- [ ] **5번째 생성 모드**로 편입할 것인가, **별도 갈래**로 둘 것인가
  - 모드로 편입하면 5-1 표에 한 줄이 추가되고 이후 레이아웃 합성을 그대로 탄다
  - 별도 갈래면 결과 화면부터 따로 만들어야 한다
- [ ] **챗봇 흐름 변경** — 업종이 옷가게일 때 "모델 입혀드릴까요?" 질문이 추가된다
  - `configs/industries.yaml` 에 의류 업종 추가
  - `configs/flow.yaml` 에 조건부 노드 추가 (`only: apparel` 형태)
- [ ] **제품 보존 원칙과의 관계**
  - 우리 원칙은 "제품 픽셀 보존"인데 이 기능은 **사람을 새로 생성**한다
  - 정리안: **옷은 보존, 사람만 생성** → `preserve` 의 변형으로 규정
  - 이 정리가 없으면 "AI가 만든 가짜 모델" 논란과 표시광고법 검토가 필요해진다
- [ ] base 모델 공유 여부 — 6-2 ①과 같은 모델을 쓰면 VRAM 을 아낄 수 있다

### 7-3. 공통 — 세 기능이 공유하는 것

| 자산 | 소유 | 확장 방법 |
|---|---|---|
| `configs/*.yaml` 레지스트리 | 기본 파이프라인 | 업종·규격 추가는 YAML 만 |
| `configs/flow.yaml` 대화 흐름 | 기본 파이프라인 | 노드 추가로 질문 삽입 |
| `src/layout.py` 레이아웃 | 기본 파이프라인 | 그대로 재사용 |
| `src/compliance.py` 법령 | 기본 파이프라인 | 그대로 재사용 |

> **레지스트리와 flow.yaml 을 수정할 때는 서로 알려주세요.** 세 기능이 같은 파일을 건드립니다.

## 8. 검증 계획

### 8-1. 자동으로 측정되는 것

모델 없이도 지금 측정 가능하거나, 모델을 붙이면 스크립트로 자동화되는 지표다.

| 지표 | 측정 방법 | 목표 |
|---|---|---|
| **금칙어 위반율** | `compliance.scan()` 을 생성 문구에 적용 | 0% |
| **글자수 상한 준수율** | 규격별 `max_headline_chars` 대조 | 100% |
| 텍스트 점유 면적 | 레이아웃 계산값 | 20% 이하 |
| 생성 시간 | 파이프라인 계측 | 1장 15초 이내 |
| VRAM 피크 | `torch.cuda.max_memory_allocated` | 8GB 이하(로컬) |
| 제품 보존율 | 누끼 마스크 밖 픽셀 변화량 | 실험으로 기준선 설정 |

> ⭐ **금칙어 위반율은 이 프로젝트의 강점입니다.** 룰 엔진이 이미 동작하므로
> LLM 출력에 그대로 돌리면 숫자가 나옵니다. 생성형 AI 프로젝트에서 정량 지표를
> 뽑기 어려운데, **"규칙 주입 전 X% → 후 Y%"** 그래프를 만들 수 있습니다.

### 8-2. 주관 평가

팀원 3인 **블라인드 5점 평가**. 항목: 적합도 · 자연스러움 · 문구 품질.
같은 입력에 대해 후보별 결과를 섞어서 제시한다.

### 8-3. 실험 목록

| # | 실험 | 결정하는 것 | 우선순위 |
|:---:|---|---|:---:|
| 1 | 배경 교체 방식 — Inpainting vs ControlNet vs 단순 합성 | 6-2 ①② | 2 |

| 3 | LLM 문구 품질 비교 | 6-2 ④ | 2 |

## 1. 현재 이미지 경로와 끊긴 지점

```
주문서 완성
   ↓
[버튼] 광고 이미지 만들기
   ↓
문구 3개 생성 (copy_gen 직접 호출)   ← 화면에 안 보여줌 · ads.save() 안 부름 → ad_id 없음
   ↓
copies[0] 자동 사용                  ← ❌ 끊김 1: 사장님이 고르지 않는다
   ↓
감성 피드형 · 정보 포스터형 생성      ← 한 형태 실패 시 return False (성공한 것도 버려짐)
   ↓
화면에 두 장 표시                    ← ❌ 끊김 2: 여기서 끝
                                       선택 없음 · 수정 없음 · 저장 없음 · 다운로드 없음
```

**문구 경로에는 이미 있는데 이미지 경로에만 없는 것**

| 기능 | 문구 경로 | 이미지 경로 |
|---|---|---|
| 후보 여러 개 보여주기 | ✅ 3개 | ❌ 문구를 아예 안 보여줌 |
| 손님 패널 순위 | ✅ (#14) | ❌ |
| 사장님 선택 | ✅ `ads.choose_copy` | ❌ |
| 다시 만들기 | ✅ `revise_view` (선택지 5 + 자연어) | ❌ |
| DB 저장 | ✅ `_make_copies` → `ads.save` | ❌ `copy_gen` 직접 호출 (DB 미기록) |
| 파일 저장 | ❌ | ❌ 부품은 있으나 미연결 |
| 다운로드 | ❌ | ❌ |

| 부품 | 하는 일 | 지금 |
|---|---|---|
| `result_store.save_result(img) -> path` | `data/results/ad_{타임스탬프}.png` 저장, 경로 반환 | 아무도 안 부름 |

### 1-2. 그런데 "연결만" 으로 끝나지 않는 이유 — 구멍 4개

**정확한 표현**: 파일 저장과 DB 기록을 위한 **기초 부품은 이미 있다.**
**화면 연결과 광고 ID 관리, 중복 저장, 부분 실패 처리는 추가 구현이 필요하다.**

| # | 구멍 | 코드 근거 | 어디서 다루나 |
|---|---|---|---|
| 1 | **광고 ID 가 없거나 남의 것** — `_make_images()` 는 `copy_gen.generate()` 를 직접 부르고 `ads.save()` 를 안 부른다. `ad_id` 가 아예 없거나, 앞서 만든 다른 광고의 `ad_id` 가 세션에 남아 그 광고에 이미지가 붙는다 | `app.py` `_make_images` 초입 (`copy_gen.generate` 직접 호출) | §2·§9 |
| 2 | **문구를 바꾸면 이미지도 다시 만들어야 한다** — 문구가 이미지에 박혀 있다. 그런데 `generate_ad()` 는 사진 생성과 조판이 한 함수에 묶여 있어서, 조판만 다시 할 방법이 없다 | `pipeline.py` `generate_ad` (→ PR-A 에서 분리, §4-2-1) | §4 |
| 3 | **한 형태가 실패하면 성공한 것도 사라진다** — for 루프 안에서 `return False` 라 먼저 만든 감성형이 화면 상태에 안 담긴다 | `app.py` `_make_images` 의 `for style in STYLES` 루프 | §7 |
| 4 | **저장 위치가 로컬 폴더** — 발표·시연은 되지만 배포 환경에서는 서버가 재시작되면 사라진다 | `result_store.py:15` | §5 |

## 2. 목표 화면 흐름

```
① 주문서 완성
      ↓
② [광고 이미지 만들기] 버튼
      ↓
③ 문구 후보 3개 생성 · 표시        ← 신규
   ⚠️ 반드시 _make_copies() (또는 같은 저장 경로) 를 거친다 → 이 시점에 ad_id 가 생긴다
   └ (선택) [손님 12명에게 물어보기] — 문구 경로와 같은 부품 재사용
      ↓
④ 사장님이 문구 1개 선택 [이걸로 만들기]   ← 신규. 여기서 이미지 생성이 시작된다
   └ ads.choose_copy(ad_id, headline)
      ↓
⑤ 생성 중 (감성 피드형 · 정보 포스터형 — 각각 독립 실행 §7)
      ↓
⑥ 두 형태 나란히 표시 + 각각 [이걸로 할게요]
      ↓
⑦ 선택한 형태에 대해
   ├ [저장]      → result_store.save_result → ads.add_image(ad_id, path)
   ├ [다운로드]  → PNG 내려받기
   └ [다시 만들기] → ⑧
      ↓
⑧ 수정 요청 (선택지 + 자연어)
   └ 무엇을 바꿀지에 따라 ③ 또는 ⑤ 로 되돌아간다 (→ §4)
```

### 2-1. 광고 ID 계약 (구멍 1)

- 이미지 경로도 문구를 만들 때 **반드시 `_make_copies()` 또는 같은 저장 경로**를 거친다.
  `copy_gen.generate()` 직접 호출은 금지 — DB 에 문구가 안 남고 `ad_id` 도 안 생긴다.
- **이미지를 저장하기 전에 현재 광고의 `ad_id` 가 존재해야 한다.**
- 새 주문서로 광고를 만들면 **새 `ad_id`** 를 쓴다. 세션에 남은 이전 `ad_id` 를 재사용하지 않는다.

### 2-2. 문구 선택 계약 — 어느 후보인지 정확히 짚는다

현재 `ads.choose_copy(ad_id, headline)` 는 **`headline` 문자열만 비교**합니다
(`ads.py:85` — `row.chosen = 1 if row.headline == headline else 0`).
제목이 같고 부제만 다른 후보가 나오면 **둘 다 선택 처리**됩니다. 생성 프롬프트가 서로 다르게
쓰라고 요구할 뿐, 코드에서 중복을 막지는 않습니다.

- 사장님이 고른 **정확한 후보 한 건**을 식별해야 한다.
- `headline` 문자열 대신 **`CopyRow.id`** 로 선택하는 방식을 권장한다
  (`db.py:119` — 이미 primary key 로 존재).
- 화면도 같은 식별자로 "지금 고른 문구"를 들고 있어야 한다 — 이미지 생성·재조판에 그대로 넘긴다.

### 2-3. 무엇을 언제 실행하나 — 병렬 가능 구간

8/13 논의에서 **"이미지 생성과 패널 평가를 동시에 돌리면 체감 대기가 줄겠다"**는 제안이 있었습니다.
사진 재료는 문구와 무관하므로 실제로 겹칠 수 있습니다.

| # | 규칙 |
|---|---|
| 1 | 문구 선택 전에는 **최종 compose(조판)를 실행하지 않는다** |
| 2 | 다만 사장님이 "광고 이미지 만들기"를 시작했다면, **문구와 무관한 사진 재료 생성은 패널 평가와 병렬 실행할 수 있다** |
| 3 | 패널 추천과 사장님 선택이 끝난 뒤, **선택한 문구로 compose 만** 실행한다 |
| 4 | 생성한 사진 재료는 **문구를 바꿔도 재사용**한다 (§4-1) |
| 5 | ⚠️ 현재 `generate_ad()` 는 생성과 조판이 묶여 있으므로, **이 병렬화는 PR-A 분리 이후 가능**하다 |

```
[병렬]  사진 재료 생성 (배경·누끼, 45~60초)  ─┐
        패널 평가 (12명, 1분)                ─┴→ 사장님 문구 선택 → compose 만 실행
```

얻는 것 — 45~60초와 1분이 겹쳐 체감 대기가 줄고, 문구를 바꿔도 사진 재료를 다시 만들지
않으며, `copies[0]` 을 미리 얹는 문제도 생기지 않습니다. **PR-A 의 "생성과 조판 분리" 목적과
정확히 맞습니다.**

⚠️ 이건 설계이지 현재 동작이 아닙니다. **PR-A 이전에는 약속할 수 없습니다.**

## 3. 문구 선택과 패널의 역할

### 3-1. 이건 새로 발견한 문제가 아니다 — 8/13 팀 논의

문구를 첫 번째 것만 쓰는 문제는 **2026-08-13 아인님 UI/UX 설계안**에서 이미 지적됐고,
**패널 평가 결과를 문구 선정에 반영하는 방향에 고귀한·건오님도 동의**했습니다.
이 문서는 그 합의를 코드에 연결하는 작업입니다.

당시 설계안의 화면 흐름:

```
문구 후보 3개 → 패널이 순위·추천 제시 → 사장님이 "1위 문구로 할게요" 또는 다른 문구 선택
             → 선택한 문구를 감성형·포스터형 모두에 사용
```

**그런데 현재 코드는 선택한 문구가 이미지 생성으로 연결되지 않고, 여전히 `copies[0]` 을 씁니다**
(`app.py` `_make_images` — `pipeline.generate_ad(brief, store, copies[0], ...)`). 합의는 있었는데 구현이 안 된 상태입니다.

당시 **"이미지 생성과 패널 평가를 동시에 돌려 체감 대기를 줄이자"**는 제안도 함께 나왔습니다 —
이 문서 §2-3 에서 다룹니다.

### 3-2. 문구 선택 규칙

| # | 규칙 |
|---|---|
| 1 | 패널을 실행하면 **1위 문구를 기본 추천**한다 |
| 2 | **사장님이** 1위 또는 다른 문구를 **최종 선택**한다 |
| 3 | 선택한 문구를 **감성형·포스터형 모두**에 사용한다 |
| 4 | **패널을 실행하지 않아도** 사장님이 직접 문구를 선택할 수 있다 |
| 5 | 아무 문구도 선택하지 않았으면 **이미지를 만들지 않고 선택을 안내**한다 |
| 6 | **`copies[0]` 자동 사용 금지** |

규칙 4가 필요한 이유: 패널은 1분·60콜이 듭니다. 급한 사장님은 건너뛸 수 있어야 합니다.

규칙 2가 필요한 이유: 후보 간 점수 차이가 재실행 흔들림(0.7)보다 작을 때가 있습니다
(실측 2026-08-13, 방문의향 49.7~54.0). 그럴 때는 "셋이 비슷했습니다"라고 알리고 사장님이 고릅니다.

### 3-3. 패널이 지금 하지 않는 것

**포스터 전체를 패널이 평가하는 기능**은 8/13 논의에서도 나왔지만, 수호님 `evaluator` 계약 변경이
필요하다는 이야기가 있었습니다. 현재 패널은 문구만 보고 이미지는 보지 않습니다
(`evaluator.py` — "광고 이미지는 보지 않았다"). **이번 연결 작업과 분리해 후속 범위로 둡니다** (§10).

## 4. 다시 만들기 — 무엇을 유지하고 무엇을 바꾸나

| 항상 유지 | 피드백에 따라 변경 |
|---|---|
| 상품 (사진·제품명) | 문구 (다시 생성 또는 다른 후보 선택) |
| 가격·날짜·이벤트 등 **사장님이 말한 사실** | 톤 (`brief.tone`) |
| 가게 정보 | 조판 (글자 위치·크기 — compose 규칙 안에서) |
| | 사진 보정 (사진을 다시 만들 때만) |

### 4-1. "문구만 바꾸면 이미지 재생성 없음" 은 틀린 말이다 (구멍 2)

문구는 **이미지에 글자로 박혀 있습니다.** 문구를 바꾸면 **최종 광고 이미지는 반드시 다시 만들어야**
합니다. 기존 글자가 박힌 PNG 를 그대로 쓸 수는 없습니다.

**정확한 표현**

> 문구만 바꿀 때는 **GPT 이미지 API 나 배경 생성 모델을 다시 호출하지 않는다.**
> 기존 사진 재료를 재사용하고 **compose(조판)만 다시 실행한다.**

| 단계 | 문구만 바꿀 때 |
|---|---|
| 사진 판정 (`route_photo`) | 재사용 — 다시 안 함 |
| 누끼 (`remove_background`) | 재사용 |
| 배경 생성 (확산 모델 / 이미지 API) | **재사용 — 여기가 비싼 곳** |
| 포스터 기획 (`plan_poster`, LLM) | **재사용** — 아래 확정 |
| **조판 (`compose_ad` / `generate_poster` 렌더)** | **다시 실행** |

**`poster_plan` 재호출 규칙 — 확정**

근거: `plan_poster()` 는 **선택한 문구를 입력받지 않습니다**
(`poster_plan.py:74~83` — `shop·industry·product·situation·tone·extra·transcript`).
문구는 그 다음 렌더 단계에서 `generate_poster(headline=copy.headline)` 로 따로 들어갑니다
(`poster.py:45`). 즉 기획안과 문구는 애초에 분리되어 있습니다.

| 바뀐 것 | `plan_poster` |
|---|---|
| **문구만** | **재사용** — 포스터 렌더만 다시 실행 |
| 톤·상품·상황 등 `plan_poster` 입력 | **변경된 입력으로 다시 호출** |
| "디자인 자체를 다르게" 요청 | **수정 요청을 입력에 실어서** 다시 호출 — 아래 |

⚠️ **"디자인을 다르게" 는 재호출만으로 부족합니다.** `plan_poster()` 는 현재 수정 요청
(`brief.feedback`)을 입력받지 않습니다 (`poster_plan.py:74~83`). 그냥 다시 부르면 **같은 입력을
그대로 다시 넣는 셈**이고, 다른 결과가 나오길 우연에 기대는 것입니다.

- 디자인 변경 요청은 **`plan_poster` 의 새 feedback 인자 또는 기획 프롬프트 입력에 명시적으로
  전달**한 뒤 다시 호출한다.
- **같은 입력을 무작정 재호출해 우연히 다른 결과가 나오길 기대하지 않는다.**

### 4-2. 그래서 코드 구조 변경이 필요하다

현재 `pipeline.generate_ad()` 는 **사진 생성과 조판이 한 함수에 묶여** 있습니다
(`pipeline.py:84~118` → `_simple_ad` → `compose_ad`). 이대로면 문구만 바꿔도 배경 생성부터 전부
다시 돌아 **비용과 20~30초가 또 나갑니다.**

실현하려면 둘 중 하나가 필요합니다 [팀 결정 필요]

| 방법 | 내용 | 비고 |
|---|---|---|
| (가) 사진 재료 캐시 | 생성된 배경·누끼를 세션이나 파일에 보관했다가 조판에 다시 넣는다 | 코드 변경 작음 |
| (나) 생성/조판 단계 분리 | `generate_ad()` 를 "재료 만들기" + "조판하기" 두 단계로 나눈다 | 구조가 깔끔, 변경 큼 |

**따라서 이 작업은 단순 화면 연결이 아니라 `pipeline` 변경을 포함합니다.**

### 4-2-1. PR-A 구현 결과 (2026-08-19, 로컬 커밋 `820684d`)

(나) 생성/조판 단계 분리로 갔습니다. `pipeline.py` 인터페이스:

```python
@dataclass(frozen=True)
class SimpleMaterials:   # 감성형 재료
    product: Image | None
    background: Image

@dataclass(frozen=True)
class PosterMaterials:   # 포스터형 재료
    product: Image | None
    plan: PosterPlan
    shop: str
    info: str

AdMaterials = SimpleMaterials | PosterMaterials

prepare_materials(brief, store, style) -> AdMaterials   # 비싼 것 전부 — 문구를 모른다
render_ad(materials, copy) -> Image                     # 싼 것만 — 문구가 처음 쓰이는 곳
generate_ad(brief, store, copy, style) -> Image         # 기존 호출부 호환 = render_ad(prepare_materials(...))
```

- 기존 호출부 3곳(`app.py`·`eval`·테스트)은 `generate_ad` 시그니처가 그대로라 **무변경**
- 회귀 18개 + 계약 4개(재료 재사용 · 문구 전달 · plan 재사용 · 변경 brief 전달) = 22 passed
- 재료 이미지는 `with Image.open() as f: f.copy()` 로 파일과 분리 — 세션에 오래 살아도 핸들 안 남음
- **넣지 않은 것**: 사진 분석 공유(감성·포스터가 누끼를 각각 1회씩 = 2회 도는 것). 화면 호출 방식과
  맞물려 후속으로. 비전 판정은 이미 1회.

## 7. 실패 흐름

| 상황 | 처리 |
|---|---|
| 문구 생성 실패 | 이미 있는 처리 유지 — 에러 문구 + stub 프로필 안내. **이미지 단계로 넘어가지 않는다** |
| 이미지 두 형태 모두 실패 | 안내 + 재시도 버튼. 선택한 문구는 유지 (다시 고르게 하지 않는다) |
| **한 형태만 성공** (구멍 3) | 아래 참조 |
| 저장 실패 (디스크·DB) | 화면에 이미지가 남아 있으므로 **다운로드는 계속 가능**해야 한다. "저장에 실패했습니다. 다운로드는 가능합니다" |
| 다운로드 실패 | 브라우저 문제 — 안내만 |
| GPU·모델 없음 | 이미 있는 처리 유지 (#18 그물) |

### 7-1. 한 형태만 성공하는 경우 (구멍 3)

**현재**: `_make_images()` 는 for 루프 안에서 한 형태가 예외를 내면 즉시 `return False` 합니다
(`app.py:437~443`). 감성형이 20초 걸려 성공한 뒤 포스터형이 실패하면 **감성형까지 화면에서 사라집니다.**

**계약**

- 감성 피드형과 정보 포스터형은 **각각 독립적으로 실행**한다. 하나의 실패가 다른 하나를 취소하지 않는다.
- **하나만 성공해도 성공한 결과는 화면에 남고, 저장·다운로드할 수 있다.**
- 실패한 형태는 그 형태만 안내한다 — "정보 포스터형은 만들지 못했습니다" + 그 형태만 재시도.

**원칙**: 뒤 단계가 실패해도 앞 단계 결과를 잃지 않습니다. **1분 걸려 만든 이미지를 남의 실패로 날리지 않습니다.**

**실증 (2026-08-19 전체 스모크)**: 팔레트 빈칸 버그(→ #35)로 포스터형이 실패하자 **성공했던 감성형까지
화면에서 사라졌습니다.** 위 계약이 필요한 이유가 실제로 나타난 첫 사례입니다.

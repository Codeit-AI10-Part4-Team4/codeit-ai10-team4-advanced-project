## 2. 기본 정보 등록

가게 단위로 고정되며 즉시 답변 가능한 항목만 사전에 수집한다. 최초 1회 등록 후
재입력을 요구하지 않는다.

| 항목 | 필수 | 활용처 |
|---|:---:|---|
| 업종 | ✅ | 문구·이미지 양쪽 |
| 상호 | ✅ | 문구·전단지 |
| 주소 | — | 상권 조회 → AI 페르소나. 미입력 시 `"서울"` |
| 연락처 | — | 전단지·POP |

**한 사용자가 다수의 가게를 보유할 수 있도록 설계한다.** 복수 업장을 운영하는
사업자를 고려한 것이다. 등록 정보는 수정 가능하다.

**업종 목록** — `configs/industries.yaml` 에 **30개 + 기타** 를 정의한다.

- 음식 10 / 소매 10 / 서비스 10 을 사업체 수가 많은 순으로 배치했다
- 근거는 국세청 100대 생활업종이다. 다만 전체 1위인 통신판매업은 제외했다 —
  온라인 판매업으로 "오프라인 동네 매장" 이라는 대상과 부합하지 않는다
- 목록에 없는 업종은 **기타** 를 선택하고 직접 입력한다. 이 경우 입력값을
  반드시 받는다. 미입력 시 프롬프트에 업종이 "기타" 로 전달되어 LLM 이
  업종을 파악하지 못한 상태로 문구를 생성하게 된다
- **주소는 현재 서울만 지원한다.** 상권 데이터가 서울 기준이므로, 서울 외 주소는
  등록 단계에서 반려한다 (조회 단계에서 실패하는 것을 사전에 차단)

## 3. 챗봇

### 3-1. 입력 방식

자연어 입력을 기본 경로로 하며, 선택지는 보조 수단으로 제공한다.

- 입력창에 예시 문구를 **플레이스홀더**로 표시한다 (실제 입력값이 아닌 회색 안내 문구)
  - `예: 크로플 신메뉴 나왔어요, 인스타에 올릴 사진 만들어줘`
- 선택지 클릭은 **필수가 아니다.** 자연어로 답변해도 되며, 표현이 어려울 때만 사용한다

### 3-2. 선택지 구성

| 단계 | 생성 주체 | 내용 |
|---|---|---|
| 1단계 | **고정** | `[광고 이미지 만들기]` `[광고 문구 만들기]` |
| 2단계 이후 | **LLM** | 대화 맥락에 따라 매 턴 동적으로 생성 |

2단계 이후를 LLM 이 선택지를 생성하는 근거는 다음과 같다. 상황별로 확인해야 할 항목이
달라 선택지를 사전에 열거할 경우 경우의 수를 감당할 수 없으며, 목록에 없는
상황이 발생하면 대응이 불가능하다.

### 3-3. 무엇을 물을지는 코드가 결정한다

질문 대상 선정을 LLM 에 위임할 경우, 이미 답변받은 항목을 재차 질문하거나
확인해야 할 항목을 누락하는 문제가 발생한다. 따라서 **질문 대상은 코드가
결정하고, LLM 은 이를 자연스러운 문장으로 변환하는 역할만 수행한다.**

항목은 두 층으로 구분한다.

| 구분 | 항목 | 처리 |
|---|---|---|
| **필수** | 상품(`product`) · 가격(`price`) | 확보될 때까지 질문한다. 없으면 생성이 불가능하다 |
| **보조** | 상황(`situation`) · 느낌(`tone`) | **각 1회만 질문**하고 응답 여부와 무관하게 진행한다 |

보조 항목을 1회로 제한하는 근거는 다음과 같다. 계속 질문할 경우 사용자가
답변을 회피할 때 대화가 순환한다. 질문 이력은 별도로 기록하여 재질문을 차단한다.

**필수 항목이 확보되는 즉시 생성 버튼이 활성화된다.** 챗봇이 보조 항목을
질문하는 중에도 사용자는 언제든 대화를 종료하고 생성을 요청할 수 있다.

### 3-4. 발화 원문 보관

슬롯은 형식이 고정되어 있어 담기지 않는 정보가 발생한다.

```
발화: "단골분들이 매콤한 걸 좋아하셔서 이번에 낸 건데, 젊은 분들도 좀 왔으면 좋겠어요"
슬롯: tone = "매운"        ← 대부분의 정보가 소실된다
```

따라서 **발화 원문을 전량 별도 보관하여 생성 프롬프트에 함께 전달한다.**

| 구분 | 역할 |
|---|---|
| 슬롯 (형식 고정) | 검증 · 저장 · 조건 판단. 수신 측이 신뢰하고 사용할 수 있다 |
| 원문 (자유 형식) | 뉘앙스 보존. 생성 프롬프트에 원문 그대로 주입한다 |

슬롯 항목을 늘리는 대신 원문을 보관하는 방식을 채택했다. 항목을 늘리면 질문이
증가해 대화가 길어지며, 그럼에도 누락되는 정보는 계속 발생하기 때문이다.

### 3-5. LLM 응답 형태

매 턴 **추출 결과 · 메시지 · 선택지**를 함께 반환한다.

```json
{
  "extracted": { "tone": "따뜻한" },
  "message": "따뜻한 느낌으로 만들어드릴게요.",
  "options": ["감성적으로", "포근하게"]
}
```

`extracted` 를 앞에 배치한다. 메시지를 먼저 생성하면 질문 작성에 치우쳐
발화에 이미 포함된 정보를 추출하지 않고 재질문하는 현상이 발생한다.

추출된 값은 항목별로 재검증하며, 검증에 실패한 항목만 폐기하고 나머지는 반영한다.

### 3-6. 개발용 표시

**개발 단계에서는 화면 우측에 주문서를 매 턴 노출한다.** LLM 이 사용자 의도를
정확히 해석했는지 육안으로 검증하기 위한 장치이며, 배포 시 제거한다.

## 4. 문구 생성

**입력**: 주문서 전체 — 슬롯과 **발화 원문**, 그리고 해당 가게의 최근 광고 이력

**출력**: 후보 **3건**, 각 건은 헤드라인과 서브로 분리된다

```
1. 헤드라인  겨울 감성 크로플
   서브      지금 4,500원
2. ...
3. ...
```

분리 출력의 근거는 다음과 같다. 이미지에 문구를 배치할 때 헤드라인은 크게,
서브는 작게 처리해야 하므로 단일 문자열로 전달할 경우 이미지 담당이 분할
기준을 판단할 수 없다.

**표시 선택지**: `[헤드라인만]` `[헤드라인 + 서브]`

**가격 처리 규칙**

- 사용자가 반드시 입력한다 (선택지·자연어 무관)
- 가격이 불필요한 광고(오픈·가게 홍보 등)는 **0원**으로 입력한다
- **0원인 경우 문구·이미지에 가격을 표시하지 않는다**
- **LLM 의 가격 임의 생성을 차단한다.** 미존재 가격 표기는 표시광고법 위반에 해당한다
- **0 은 사용자가 명시적으로 입력한 경우에만 저장한다.** 언급이 없을 때 LLM 이 0 을
  기입하면 가격을 질문하지 않고 진행하게 되므로, "미언급"과 "가격 없음"을 구분한다

**발화 원문 활용**

슬롯과 함께 원문을 프롬프트에 주입한다. 슬롯만으로는 도출되지 않는 표현이 확보된다.

```
원문: "단골분들이 매콤한 걸 좋아하셔서 … 젊은 분들도 좀 왔으면 좋겠어요"
     ↓
문구: "신메뉴로 젊은 맛을 느껴보세요"
     "단골들의 사랑을 받은 신메뉴"
```

단, 원문 주입 시에도 **없는 사실의 생성은 금지**한다.

## 5. 산출 데이터 명세 ⭐

> **이 장이 다른 담당자와의 계약이다.** 필드를 추가·삭제·개명할 때는 PR 전에 공유한다.
> 이전 `04_넘겨줄_데이터.md` 를 대체한다 (해당 문서는 `docs/archive/` 로 이동).

산출물은 2종이다. 생성 주체와 생성 시점이 다르다.

| | 생성 주체 | 시점 | 개수 |
|---|---|---|---|
| **`Store`** | 프로필 입력 폼 | 최초 1회 등록 후 재사용 | 사용자당 다수 |
| **`AdBrief`** | 챗봇(NLU) | 광고 생성 시마다 | 가게당 다수 |

### 5-1. 프로필 입력 산출물 — `Store`

| 필드 | 타입 | 필수 | 값 | 설명 |
|---|---|:---:|---|---|
| `id` | int | ✅ | `1` | 가게 식별자 |
| `user_id` | int | ✅ | `1` | 소유 계정 |
| `industry` | str | ✅ | `"cafe"` | `configs/industries.yaml` 의 id |
| `industry_note` | str | — | `""` | `industry` 가 `other` 일 때 직접 입력한 업종명 |
| `name` | str | ✅ | `"연남 크로플"` | 상호 |
| `address` | str | — | `"서울시 마포구 연남동 1-2"` | 입력은 선택이나 **미입력 시 `"서울"` 로 대체**되어 값은 항상 존재한다 |
| `phone` | str | — | `"02-333-4444"` | 연락처 |

**계산 속성** (저장하지 않는다)

| 속성 | 값 | 설명 |
|---|---|---|
| `industry_label` | `"카페·디저트"` | 사람이 읽는 업종명. `other` 면 `industry_note` 를 반환 |

### 5-2. NLU 산출물 — `AdBrief` (주문서)

| 필드 | 타입 | 필수 | 값 | 설명 |
|---|---|:---:|---|---|
| `goal` | str | ✅ | `"copy"` | `"image"` \| `"copy"`. 고정 버튼으로 결정 |
| `product` | str | ✅ | `"크로플"` | 홍보 대상. 대화로 확보 |
| `price` | int | ✅ | `4500` | 원 단위. **0 = 광고에 가격 미표시** |
| `situation` | str | — | `"신메뉴"` | 자유 텍스트. 고정 목록 아님 |
| `tone` | str | — | `"따뜻하고 감성적인"` | 자유 텍스트. 고정 목록 아님 |
| `extra` | str | — | `""` | 그 밖의 요청 |
| `with_sub` | bool | — | `true` | 서브 문구 생성 여부 |
| `transcript` | list[str] | — | `["크로플 홍보하고싶어", "4500원", …]` | **사장님 발화 원문.** 슬롯이 담지 못한 뉘앙스 |

**계산 속성** (저장하지 않는다)

| 속성 | 값 | 설명 |
|---|---|---|
| `show_price` | `true` | `price > 0` 여부. 가격 표시 판정 |
| `items` | `[{"name": "크로플", "price": "4,500원"}]` | 가격 항목 목록. **0 원이면 `[]`** |
| `raw_utterance` | `"크로플 홍보하고싶어\n4500원\n…"` | `transcript` 를 줄바꿈으로 연결 |

**`price` 를 정수로 두고 `items` 를 계산해서 만드는 이유**

수신 측(품질 검증·이미지 생성)은 `[{"name","price"}]` 형태를 기대한다. 그러나
슬롯 자체를 목록으로 두면 **"아직 안 물어봄"과 "가격 없음"을 구분할 수 없다.**
정수 하나로 받아 `None`(미언급) / `0`(가격 없음) / `양수`(가격)를 구분하고,
전달 시점에만 목록 형태로 변환한다.

> 대화 진행 중에는 `AdBriefDraft` 상태이며 `asked`(질문 이력) 필드가 추가로 존재한다.
> 주문서로 승격(`to_brief()`)될 때 제외된다.

### 5-3. 전달 형태


### 5-4. 품질 검증(AI 손님 패널) 담당에게 넘기는 값

`06_기술계획서_품질검증.md` §5.1 (브랜치 `feat/quality-review`) 의 `EvalContext` 요청에 대한 대응이다.

**패널 구성 단계** — 저쪽이 쓰는 값은 **2개뿐**이다.

| 저쪽 필요 값 | 우리 값 | 상태 |
|---|---|---|
| 주소 | `store.address` | ⚠️ **아래 ① 참조** |
| 업종 | `store.industry` | ⚠️ **아래 ③ 참조** |

> 광고 정보로 페르소나를 만들면 "이 광고에 반응할 만한 손님"을 만들어놓고
> 그 손님에게 평가받는 자기충족이 되므로, 구성에는 주소·업종만 쓴다는 것이
> 저쪽 설계다 (`05_AI손님패널_기획.md` §6).

**평가 단계** — `evaluate(image, headline, sub, items, context)` 로 전달한다.

평가 대상은 **주문서가 아니라 완성된 광고물**이다. 저쪽 `AdContent` 주석에
"파이프라인 출력에서 조립"이라 명시되어 있다. 주문서는 광고물을 만드는 입력이고,
평가에 넘기는 것은 그 **산출물**과 "어떤 조건으로 만들어졌는지"를 설명하는 `context` 다.

| 저쪽 요청 필드 | 성격 | 우리 값 | 상태 |
|---|---|---|---|
| `headline` · `sub` | **생성 결과물** | 문구 생성기 출력 중 사용자가 고른 1건 | ✅ 제공 |
| `image` | **생성 결과물** | — | ❌ 이미지 생성 미구현 (저쪽도 현 단계 미사용) |
| `items` | 부가 정보 | `brief.items` (계산 속성) | ✅ 제공 |
| `context.industry` | 부가 정보 | `store.industry` | ✅ 제공 |
| `context.product` | 부가 정보 | `brief.product` | ✅ 제공 |
| `context.store_address` | 부가 정보 | `store.address` | ⚠️ **아래 ①** |
| `context.format` | 부가 정보 | — | ❌ **없음.** `formats.yaml` 폐기 |
| `context.style` | 부가 정보 | — | ❌ **없음.** 자유 텍스트 `tone` 으로 대체 |
| `context.mode` | 부가 정보 | — | ❌ **없음.** 사진 필드 미구현 |

**① `store_address` 는 항상 값이 존재한다 — 폴백 조건이 성립하지 않는다**

저쪽은 `store_address` 가 **`None` 일 때** 서울 평균 패널로 폴백하고 "동네 데이터
없이 평가함" 배지를 띄우도록 설계했다. 그러나 우리 쪽은 미입력 시 문자열
`"서울"` 을 채우므로 `None` 이 되지 않는다. 그 결과:

- 폴백 분기가 동작하지 않는다
- 카카오 API 가 `"서울"` 을 임의 좌표로 변환한다
- 배지가 표시되지 않는다

→ **협의 필요.** 기본값을 `None` 으로 변경하거나, 저쪽이 `"서울"` 을 폴백 신호로
인식하도록 합의한다.

**② `format`·`style`·`mode` 는 저쪽도 사용하지 않는다**

`05_AI손님패널_기획.md` §6 (브랜치 `feat/quality-review`) 에 다음과 같이 명시되어 있다.

> `format`(인스타/전단지/현수막)은 이미 `context`에 있지만 **일부러 쓰지 않습니다.**
> 채널마다 도달하는 사람이 다른 건 맞지만 서울시 상권 데이터에 채널별 도달 정보가
> 없어서, 보정하려면 계수를 지어내야 합니다.

인터페이스 안정성 목적으로 인자에 포함해 둔 것이므로 **제거 가능 여부를 확인한다.**

**③ 업종 매핑이 변경되었다 — 공유 필요**

`configs/*.yaml` 은 기본 파이프라인 소유이며, 변경 시 사전 공유가 합의 사항이다

## 6. 데이터 저장

### 6-1. DB — PostgreSQL

```
사용자 (계정)
  └─ 가게 다수 (업종 · 주소 · 상호 · 연락처)
      └─ 주문서 다수
          ├─ 생성된 문구
          └─ 이미지 경로
```

**선정 근거**

- 로그인·가게·주문서·이력이 모두 관계형 데이터에 해당한다
- GCP Cloud SQL 로 직접 연결 가능하다
- 향후 벡터 검색 도입 시 `pgvector` 확장으로 동일 DB 내에서 처리할 수 있다

**AI 페르소나 담당의 DuckDB 와 병행 운용한다.** 용도가 상이하기 때문이다. 상권
공공데이터는 1회 적재 후 읽기 전용으로 사용하는 분석 데이터이므로 DuckDB 가
적합하며, 본 서비스 데이터는 다수 사용자의 지속적인 쓰기·삭제가 발생하므로
PostgreSQL 이 적합하다.

### 6-2. 테이블 구성

총 5개 테이블로 구성한다.

```
users ──┬─< stores ──< ads ──┬─< ad_copies
        │                    └─< ad_images
```

**`users` — 계정**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | int | PK |
| `username` | str(64) | 고유값 |
| `password_hash` | str(256) | **평문 저장 금지.** 아래 방식 참조 |
| `created_at` | timestamp | |

**`stores` — 가게. 한 사용자가 다수 보유**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | int | PK |
| `user_id` | int | FK → `users.id` |
| `industry` | str(32) | `industries.yaml` 의 **id** (`cafe` 등) |
| `industry_note` | str(64) | `industry` 가 `other` 일 때 직접 입력한 업종명 |
| `name` | str(128) | 상호 |
| `address` | str(256) | 미입력 시 `"서울"` |
| `phone` | str(32) | |

**`ads` — 주문서 1건. 차기 생성 시 참조할 이력이기도 하다**

| 컬럼 | 설명 |
|---|---|
| `store_id` | FK → `stores.id` |
| `goal` | `image` / `copy` |
| `product` · `price` | 필수 항목 |
| `situation` · `tone` · `extra` | 대화에서 확보한 항목 |
| `transcript` | **사장님 발화 원문.** 줄바꿈으로 연결해 저장 |
| `created_at` | 최근 이력 조회 기준 |

**`ad_copies` — 생성된 문구.** `headline` · `sub` · `chosen`(사용자 선택 여부)
**`ad_images` — 생성된 이미지 경로.** `path`

### 6-3. 저장 방식 — 세부 규칙

**① 비밀번호는 평문으로 저장하지 않는다**

표준 라이브러리 `hashlib.scrypt` 로 해시하여 저장한다. 저장 형식은 다음과 같다.

```
0d8a8f4deef0d377107f8fc5d1903127 $ 1c59cd704f6cd96265571f52dd48...
└──────── salt (16바이트) ────────┘  └──────── scrypt 해시 ────────┘
```

- **salt 는 가입 시마다 새로 생성한다.** 동일한 비밀번호라도 저장값이 달라지므로,
  한 계정이 노출되어도 나머지 계정에 영향이 없다
- **scrypt 는 의도적으로 느리고 메모리를 많이 사용한다.** 무차별 대입 공격에 대비한 것이다
- 복호화는 불가능하다. 로그인 시에는 입력값을 동일한 salt 로 다시 해시하여 비교한다
- 비교에는 `hmac.compare_digest` 를 사용한다 (타이밍 공격 대비)
- 외부 라이브러리를 도입하지 않은 것은 표준 라이브러리로 충분하기 때문이다

**② 업종은 id 로 저장한다**

한글 라벨이 아닌 `industries.yaml` 의 id 를 저장한다.

| 경우 | `industry` | `industry_note` |
|---|---|---|
| 목록에 존재 | `cafe` | (없음) |
| 목록에 없음 | `other` | `드라이플라워 공방` |

라벨을 바꾸더라도(`카페·디저트` → `카페·베이커리`) DB 를 수정할 필요가 없다.
화면 표시 시점에만 `industries.yaml` 에서 라벨을 조회한다.

**③ 사용자 격리**

가게 조회·수정·삭제 시 `store_id` 와 함께 **`user_id` 를 반드시 대조한다.**
id 만으로 조회하면 타인의 가게에 접근할 수 있다.

**④ 연쇄 삭제**

`users` → `stores` → `ads` → `ad_copies`·`ad_images` 로 cascade 를 설정한다.
가게를 삭제하면 해당 가게의 광고 이력도 함께 삭제된다.

**⑤ 접속 대상은 환경변수로 결정한다**

`DATABASE_URL` 하나로 접속 대상이 결정된다.

| 환경 | 값 |
|---|---|
| 도커 | `postgresql+psycopg://ads:ads@db:5432/ads` (compose 가 주입) |
| 테스트 | `sqlite:///...` (임시 파일. CI 에 DB 서버가 없어도 동작) |
| 배포 | Cloud SQL 주소 |

SQLAlchemy 를 사용하므로 테스트 환경에서 SQLite 로 대체할 수 있으며, 배포 시
주소만 교체하면 코드 변경이 발생하지 않는다.

### 6-4. 이미지 파일

DB 에 저장하지 않는다. 파일 스토리지(GCS 등)에 보관하고 **DB 에는 경로만** 기록한다.

### 6-5. 이력 활용

기존 주문서·문구·이미지를 차기 생성 시 참조한다.

| 단계 | 방식 | 적용 시점 |
|---|---|---|
| **1단계** | **최근 5건**을 프롬프트에 주입 | **현재** |
| 2단계 | 벡터 검색을 통한 유사 이력 조회 | 이력 누적 후 |

건수를 제한하는 이유는 프롬프트 길이가 무한정 증가하는 것을 방지하기 위함이다.

### 7-1. 프론트엔드 교체 가능성

Streamlit 으로 구현하더라도 향후 React 전환 시 `src/` 수정이 불필요하다.
**단, 아래 조건을 준수해야 한다.**

- 대화 로직·주문서·LLM 호출은 전량 `src/app_core/` 에 배치한다
- Streamlit 은 화면 렌더링만 담당하며, `app_core` 함수를 호출하는 데 그친다
- **`app_core` 내부에 `import streamlit` 이 존재해서는 안 된다**

`AGENTS.md` 의 기존 원칙(`app_core` 는 FastAPI 없이 단독 동작)과 동일한 규칙이다.

### 7-2. 실행 환경 — Docker

Python·PostgreSQL·의존성이 전부 컨테이너 안에 있다.

```
cp .env.example .env      # OPENAI_API_KEY 를 채운다
docker compose up app     # → localhost:8501
```

| 서비스 | 내용 | 포트 |
|---|---|---|
| `db` | PostgreSQL 16 | 5432 |
| `app` | 챗봇 UI · 문구 생성 · API | 8501 / 8000 |
| `gpu` | 이미지 생성 (GPU 필요) | 8502 / 8001 |

**구성 시 처리한 사항**

| 항목 | 처리 | 근거 |
|---|---|---|
| DB 데이터 보존 | `pgdata` 명명 볼륨 | 볼륨이 없으면 컨테이너 재생성 시 가입 계정이 소실된다 |
| 기동 순서 | `healthcheck` + `depends_on` | `app` 이 `db` 보다 먼저 기동하면 연결에 실패한다 |
| DB 주소 | compose 가 `DATABASE_URL` 을 주입 | 컨테이너 내부에서 DB 호스트는 `localhost` 가 아니라 서비스명 `db` 다 |
| 코드 반영 | 소스 디렉토리 바인드 마운트 | 코드 수정마다 이미지를 재빌드하지 않기 위함 |

**보조 명령**

```
docker compose run --rm app pytest     # 테스트
docker compose run --rm app bash       # 컨테이너 내부 작업
```

### 7-3. 설정 관리 — `.env`

API 키·DB 주소 등은 코드에 넣지 않고 `.env` 로 분리한다. `.env` 는 gitignore
대상이며, 저장소에는 값이 빈 `.env.example` 만 커밋한다.

읽어들이는 방식은 실행 환경에 따라 다르다.

| 실행 방식 | 주입 주체 |
|---|---|
| 도커 | compose 의 `env_file` |
| 로컬 (`streamlit run app.py`) | `app_core/config.py` 의 `load_env()` |

`load_env()` 는 표준 라이브러리만 사용한다. `python-dotenv` 를 도입하지 않은 것은
용도가 단순 파일 파싱에 그쳐 의존성을 늘릴 실익이 없기 때문이다.

**이미 설정된 환경변수는 덮어쓰지 않는다.** 도커 실행 시 compose 가 주입한 값이
`.env` 파일의 값보다 우선해야 하기 때문이다.

### 7-4. 배포 준비

현 단계에서 GCP 를 위해 별도 설계할 사항은 없다. 다만 다음 두 가지는 현
시점부터 준수한다.

- API 키·설정은 **환경변수로 관리** (기 적용)
- 파일 저장 대신 **DB 사용** — GCP 는 인스턴스 재시작 시 로컬 파일이 소실된다

DB 는 `DATABASE_URL` 하나로 접속 대상이 결정되므로, 배포 시 Cloud SQL 주소로
교체하는 것 외에 코드 변경이 발생하지 않는다.

|---|---|---|
| 1 | 회원가입 | 아이디 · 비밀번호(8자 이상) |
| 2 | 가게 추가 | 업종 선택, 상호, **주소는 "서울"로 시작**해야 통과 |
| 3 | 광고 만들기 | `[광고 이미지 만들기]` / `[광고 문구 만들기]` |
| 4 | 챗봇 | 자연어 입력. 선택지 클릭도 가능 |
| 5 | 주문서 패널 | **화면 우측에서 매 턴 갱신되는 값을 확인** |
| 6 | 문구 만들기 | 필수 항목(상품·가격)이 채워지면 버튼 활성화. 챗봇이 추가 질문 중이어도 즉시 생성 가능 |

입력 예시: `교촌치킨에서 신메뉴를 출시했는데 적절한 문구를 추천해줘`

### 8-4. 주의 사항

**`.env` 수정 시 컨테이너 재생성이 필요하다.**

```
docker compose up -d --force-recreate app
```

`docker compose restart` 는 프로세스만 재시작하므로 환경변수가 반영되지 않는다.
설정을 변경했는데 동작이 그대로라면 이 문제일 가능성이 높다.

**데이터 초기화**

```
docker compose down -v
```

`-v` 는 DB 볼륨까지 삭제하므로 가입 계정과 등록 가게가 모두 사라진다.
평소에는 `-v` 없이 종료한다.

### 8-5. 주문서를 코드에서 받아 쓰는 경우

이미지 생성·품질 평가 담당은 화면이 아니라 **주문서 데이터**를 필요로 한다.
챗봇 완성을 기다릴 필요 없이 아래 값을 직접 만들어 개발할 수 있다.

```python
from app_core.schema import AdBrief, Store

store = Store(
    id=1, user_id=1,
    industry="cafe", name="연남 크로플",
    address="서울시 마포구 연남동 1-2", phone="02-000-0000",
)
brief = AdBrief(
    goal="image", product="크로플", price=4500,
    situation="신메뉴", tone="따뜻한",
    transcript=["크로플 신메뉴 나왔어요", "4500원이고 따뜻한 느낌으로요"],
)
```

전달되는 값의 형태는 다음과 같다.

```json
{
  "store": {
    "industry": "cafe", "name": "연남 크로플",
    "address": "서울시 마포구 연남동 1-2", "phone": "02-000-0000",
    "industry_note": "", "id": 1, "user_id": 1
  },
  "brief": {
    "goal": "image", "product": "크로플", "price": 4500,
    "situation": "신메뉴", "tone": "따뜻한",
    "extra": "", "with_sub": true,
    "transcript": ["크로플 신메뉴 나왔어요", "4500원이고 따뜻한 느낌으로요"]
  }
}
```

| 항목 | 설명 |
|---|---|
| `store.industry` | `configs/industries.yaml` 의 id |
| `store.industry_label` | 사람이 읽는 업종명 (프롬프트용). `기타`면 직접 입력값 |
| `brief.price` | **0 이면 광고에 가격을 표시하지 않는다** (`brief.show_price` 로 판정) |
| `brief.situation` · `tone` | 자유 텍스트. 고정 목록이 아니다 |
| `brief.with_sub` | 서브 문구 생성 여부 |
| `brief.transcript` | **사장님 발화 원문.** 슬롯이 담지 못한 뉘앙스가 여기 있다 |
| `brief.raw_utterance` | 위 원문을 줄바꿈으로 이어 붙인 문자열 (프롬프트 주입용) |

주소는 미입력 시 `"서울"` 로 대체되므로 항상 값이 존재한다.
`transcript` 는 생성 프롬프트에 **슬롯과 함께** 넣기를 권장한다. 슬롯만 사용하면
"젊은 손님도 왔으면", "단골이 매콤한 걸 좋아해서" 같은 정보가 반영되지 않는다.

## 10. 미결정 사항

- 최종 프론트엔드 (React 채택 여부)
- 로그인 방식 — 현재 자체 계정(아이디·비밀번호). 소셜 로그인 도입 여부 미정
- **사진 파일 업로드 경로** — 고귀한 님과 협의 필요. 현재 주문서에는 사진 필드가
  없으며, 이미지 바이너리는 JSON 으로 전달할 수 없어 별도 경로가 필요하다
- 서울 외 지역 확대 여부
- 이미 입력한 값의 수정 처리 ("아니 6000원이요" 와 같은 정정 발화)

# 타깃 사용자 및 기능 정의

> 소상공인을 위한 광고 콘텐츠 생성 서비스 · 기획 문서
> 최종 수정: 2026-08-04 · 관련: [02 광고 규제 준수 기능 설계](02_광고규제_준수기능_설계.md)

# 1. 타깃 사용자

## 1-1. 누구인가

**영세·오프라인 중심 소상공인 (동네 매장)**
음식점·카페 · 정육/반찬/청과 · 미용실/네일 · 꽃집/공방 · 학원/공부방 · 헬스장

프로젝트 요구사항의 *"오프라인 중심 사업자들이 온라인 마케팅에 쉽게 진입"* 과 일치한다.

### 온라인 셀러를 제외한 이유

| | 온라인 셀러 (제외) | **동네 매장 (타깃)** |
|---|---|---|
| 주 산출물 | 스마트스토어 대표이미지, 상세페이지 | **인스타 피드/스토리, 매장 앞 POP, 전단지, 메뉴판** |
| 사진 상태 | 그나마 스튜디오 촬영 | **형광등 아래 폰 사진** — 보정이 먼저 필요 |
| 문구 톤 | 스펙·가격 소구 | **동네 친근함, 오늘의 메뉴, 이벤트 안내** |
| 반복 주기 | 상품 등록 시 1회 | **매일/매주 반복** |

 필요한 건 *한 번 잘 만들기*가 아니라 속도와 반복 편의성이 곧 서비스 가치.

## 1-2. 업종별 실태

| 업종 | 가진 소재 | 만들어야 하는 것 | **진짜 병목** |
|---|---|---|---|
| **음식점**<br>백반·분식·치킨 | 음식 사진<br>(형광등, 스테인리스 위) | 배달앱 썸네일, 네이버플레이스,<br>매장 앞 배너 | 음식이 **맛없어 보임**<br>+ "점심특선 8,000원" 공지를 못 만듦 |
| **카페·디저트** | 음료·디저트 사진<br>(그럭저럭 예쁨) | 인스타 피드/스토리, 신메뉴 | **감성 톤 보정**과 **문구 센스**가 없음<br>**매일 올릴 소재 압박** |
| **미용실·네일** | 시술 결과 사진 **다수**<br>(인물 일부 포함) | 인스타 피드, 첫방문 할인 | 사진은 많음.<br>**여러 장 배열 + 글자 얹기**가 안 됨 |
| **정육·반찬·청과** | 상품 사진 (대충) | **가격표·특가 POP**, 전단지 | 사진이 아니라<br>**"삼겹살 100g 1,900원"을 크고 안 촌스럽게** |
| **꽃집·공방** | 상품 사진 (잘 찍음) | 인스타, 시즌 이벤트 | **시즌 연출**<br>(발렌타인·어버이날·크리스마스) |
| **학원·공부방** | **사진 소재가 없음**<br>(아이 사진은 초상권) | 전단지, 현수막, 모집 안내 | **얹을 사진이 아예 없음** |
| **헬스장·필라테스** | 시설 사진 | 등록 이벤트 포스터 | 가격·기간 정보를 **깔끔하게 배치** |

## 1-3. 실태 데이터

### 근거 A — 중소기업중앙회 「소상공인 DX·AX 현황 및 정책수요 조사」
> 2026.6.9 발표 · 소상공인 500개사

| 지표 | 수치 | 해석 |
|---|---|---|
| 디지털·AI 기술 활용 | 80.0% | 도구는 이미 쓰고 있음 |
| 활용 수준이 **"기초·입문"** | **83.3%** | 기초 30.5% + 입문 52.8% |
| 활용 분야 — 경영지원 | 54.5% | 세무·회계는 이미 정착 |
| 〃 고객응대 | 31.8% | |
| 〃 판매·유통 | 22.3% | |
| 〃 **마케팅·홍보** | **21.3%** | **가장 미개척 = 우리 자리** |
| 정부 지원사업 참여율 | 3.2% | |
| 미신청 이유 1위 — **"몰라서"** | **76.2%** | 문제의 상당수는 **정보 격차** |

### 근거 B — 「2024년 기준 소상공인실태조사」 (중소벤처기업부·통계청)

| 지표 | 수치 |
|---|---|
| 디지털·스마트 기술을 활용하는 소상공인 | 27.2% |
| 그중 온라인 판로 활용 | 49.0% |

### ⚠️ 두 조사가 충돌한다 — 발표 시 반드시 알고 있을 것

디지털 활용률이 **80.0%(중기중앙회) vs 27.2%(실태조사)** 로 크게 다르다.
전자는 "키오스크·SNS 포함 광의", 후자는 "디지털·스마트 기술" 협의라 생기는 차이다.
언론에서도 80%를 **"착시"** 로 지적하며 고도화 활용은 2~3%대라고 본다.

> → 80%를 인용할 때는 반드시 **"기초·입문 83.3%"** 를 함께 제시해 과장을 피한다.

# 2. 고충과 그래서 필요한 기능

## 고충 1. 시간이 없다

매장 운영에 바빠 홍보 기술·지식을 쌓을 시간이 없고,
외주를 맡겨도 비용 대비 효율을 체감하지 못하며 신뢰하기도 어렵다.

**→ 필요한 기능**
- **클릭 3~4번, 5분 이내 완료** — 매주 반복하므로 한 번이 길면 두 번째부터 안 쓴다
- 학습이 필요 없는 UI (교육형·설명형 금지)
- 만든 결과물 히스토리·재사용

## 고충 2. 폰으로 찍은 사진이 맛없어 보인다

| 문제 | 원인 |
|---|---|
| 입체감이 없다 | 정면 직광(플래시)은 그림자를 없애 입체감을 죽인다. 45도 측광이 필요 |
| 색이 이상하다 | 형광등은 초록끼, 백열등은 주황끼. 기준은 **5500K** |
| 지저분하다 | 배달앱 썸네일 3대 결격 사유 중 하나가 **"배경이 메뉴를 방해하는가"** |

**→ 필요한 기능**
- **화이트밸런스 자동 보정** — 모델 없이도 사진이 눈에 띄게 좋아진다
- **배경 교체 (제품 픽셀은 보존)** — "예쁘게"가 아니라 **방해 요소 제거**가 목적
- 45도 측광 연출

> ⚠️ **과하게 보정하면 안 된다.** 실물과 다르면 리뷰 불만·반품으로 돌아온다.
> 표시광고법 위반이기도 하다. → **보정 강도에 상한**을 둔다.

## 고충 3. 원하는 바를 글로 옮기기 어렵다

도구는 쓰고 있지만 활용 수준은 초기 단계(**기초·입문 83.3%**)에 머물러 있다.
`"cinematic lighting, 85mm, bokeh"` 같은 입력을 기대할 수 없다.

**→ 필요한 기능**
- **자연어 입력을 기본 동선으로** — "우리 카페 크로플, 인스타에 올릴 사진 만들어줘" 한 문장이면 충분하게
- 말에서 알아낸 항목은 건너뛰고 **모자란 것만 되묻기**
- **선택형 보조 경로** — 말로 설명하기 어려운 분을 위해 하나씩 물어보는 길을 따로 둔다
- **사진을 보고 문구를 제안** (VLM + LLM)

## 고충 4. 규격의 불확실성

| 사실 | 함의 |
|---|---|
| 채널마다 규격·안전영역이 다르다 | 인스타 스토리는 상단 20.8%·하단 28.6%가 UI에 가려진다 |
| 인스타 피드 노출이 **2025.1부터 1:1 → 4:5** 로 변경 | 세로형이 최고 성과 |
| 이미지 위 텍스트가 20%를 넘으면 | **도달 최대 50% 감소, 3일 만에 게재 중단** |
| Diffusion 모델은 **한글을 제대로 못 그린다** | 이미지 생성으로 글자를 넣을 수 없다 |

**→ 필요한 기능**
- **규격별 자동 레이아웃** — 이미지는 "글자 없는 배경"으로 만들고 한글은 따로 얹는다
- **안전영역 반영**, **텍스트 점유율 20% 경고**
- 한 소재로 **여러 규격 동시 출력**

## 고충 5. 모르고 법을 어긴다

| 사실 | |
|---|---|
| 지원사업 미신청 이유 1위 | **"몰라서" 76.2%** (참여율 3.2%) |
| 샐러드집이 무심코 쓰는 **"다이어트"** | 식품표시광고법 제8조 위반 |
| "동네 최고", "1위" | 객관적 근거 없으면 표시광고법 위반 |

법을 어기는 것은 악의가 아니라 **몰라서**다.

**→ 필요한 기능**
- **생성 단계에서 금칙 표현 차단** — 애초에 위반 문구가 안 나오게
- 발견 시 **대체 표현 원클릭 교체**
- 요청 시 **적용 법령과 근거 제시** (RAG로 확장)
- **가격은 AI가 생성하지 않고 사장님이 직접 입력**

> 상세 설계는 [02 광고 규제 준수 기능 설계](02_광고규제_준수기능_설계.md).

# 3. 핵심 인사이트 — 두 개의 축

업종을 나열하면 기능이 안 보인다. **두 축으로 재배열하면 아키텍처가 도출된다.**

```
                        사진 소재 있음
                              │
            [카페]            │            [음식점]
            [꽃집·공방]        │            [정육·반찬]
            [미용실]          │            [헬스장]
                              │
       이미지 중심 ───────────┼─────────── 정보 중심
       (감성·분위기)          │            (가격·조건 전달)
                              │
                              │            [학원·공부방]
                              │            [특가 POP]
                              │
                        사진 소재 없음
```

**세로축 (소재 유무) → 이미지 파이프라인이 갈린다**
- 있음: 제품 픽셀 **보존** + 배경·조명만 교체 (Inpainting / ControlNet)
- 없음: 글자를 얹을 **배경만 생성** → 이 경우에만 text-to-image 가 정당하다

**가로축 (이미지 vs 정보) → 레이아웃 엔진이 갈린다**
- 이미지 중심: 사진 크게, 문구 짧게, 여백 넉넉
- 정보 중심: 글자가 주인공. 가격 크게, 가독성 최우선, 인쇄 고려

> 이 축이 배치 패턴 4종의 **존재 근거**다. 임의로 정한 게 아니다.

# 4. 기능 우선순위

## P0 · 없으면 서비스가 성립 안 됨

- 자연어 입력으로 시작 · 모자란 항목만 되묻기
- 선택형 보조 경로 (말로 설명하기 어려운 분용)
- 제품 보존 + 배경·조명 교체
- 화이트밸런스 자동 보정
- 사진 보고 문구 제안 (VLM + LLM)
- 규격별 자동 레이아웃 (한글 합성)
- 금칙 표현 차단

## P1 · 실사용 가능성을 가름

- 3안 제시 → 선택
- 문구만 수정 → 즉시 재출력
- 가격·조건 직접 입력
- 채널별 이미지 의도 반영 (식욕 / 신뢰 / 분위기)
- 안전영역 반영 · 텍스트 20% 경고
- 대체 표현 원클릭 교체
- 소재 없이 배경만 생성 (학원 등)
- 레퍼런스 이미지 입력

## P2 · 여유 되면

- 결과물 히스토리·재사용
- 여러 규격 동시 출력
- 적용 법령 근거 제시 (RAG)
- 45도 측광 연출 · 보정 강도 상한
- 다중 이미지 콜라주 (미용실)
- 시즌 테마 프리셋 (꽃집·공방)
- 얼굴 감지 경고 (초상권)

## 만들지 않을 것

| 제외 | 이유 |
|---|---|
| SNS 자동 업로드 | 계정 연동 복잡도가 본질과 무관 |
| 정교한 편집기 | 활용 수준이 기초·입문 단계라 쓰기 어렵다 |
| 로고 디자인·동영상 | 범위 밖 |
| 스케치 → 이미지 | 아래 6장 참조 |

# 5. 프로젝트 요구사항 기능 매핑

가이드의 '구현 기능 예시' 5개 중 **4개를 커버**한다 (요구사항 최소치는 1개).

| 요구사항 예시 기능 | 대응 | 우리 구현 |
|---|:---:|---|
| 상품 이미지 → **광고 문구 제안** | ✅ | VLM 이 사진을 읽고 업종·톤과 조합해 3안 제안 |
| 광고 이미지 1: **텍스트 입력만** | ✅ | `scene` 모드 — 사진 소재가 없는 학원 등 |
| 광고 이미지 2: **레퍼런스 이미지** | ✅ | `reference` / `preserve_ref` 모드 (IP-Adapter) |
| 광고 이미지 3: **입력 이미지 보존** | ✅ | `preserve` 모드 — **핵심 기능** |
| 광고 이미지 4: **스케치** | ❌ | 아래 제외 근거 |

## 생성 모드는 사용자가 고르지 않는다

모드 선택 UI 를 만들면 기초·입문 단계 사용자가 헤맨다. **무엇을 올렸는지로 자동 결정**한다.

| 제품 사진 | 레퍼런스 | → 모드 | 붙일 모델 | 대응 요구사항 |
|:---:|:---:|---|---|---|
| ✓ | ✗ | `preserve` | SDXL Inpainting | 이미지 3 |
| ✓ | ✓ | `preserve_ref` | 위 + IP-Adapter | 이미지 2 + 3 |
| ✗ | ✓ | `reference` | SDXL + IP-Adapter | 이미지 2 |
| ✗ | ✗ | `scene` | SDXL text-to-image | 이미지 1 |

넷 다 **SDXL 하나 위에서 conditioning 만 다르다.** 모델을 한 번만 올리면 되므로
모드 추가의 한계 비용이 낮다.

## 스케치 기능 제외 근거

- **시나리오가 비현실적** — 동네 매장 사장님이 스케치를 그려 광고를 만들지 않는다
- **UI 비용이 별개** — 캔버스 드로잉이 필요하고 모바일에서 특히 쓰기 어렵다
- **이미 4개를 커버** — 요구사항 최소치(1개)를 크게 상회한다

> 여력이 생기면 P2 로 재검토. ControlNet(scribble)이라 모델 스택은 동일하다.

# 6. 서비스 흐름 — 챗봇

## 6-1. 왜 챗봇인가

폼 방식은 한 화면에 업종·사진·규격·스타일·상품명·가격이 전부 보인다.
**기초·입문 단계가 83.3%인 사용자에게는 선택지가 한꺼번에 보이는 것 자체가 부담**이다.
챗봇은 한 번에 하나만 묻는다.

대신 약점 두 가지를 보완해야 한다.

| 약점 | 대응 |
|---|---|
| 되돌아가기가 어렵다 | 대화의 이전 답변을 **클릭하면 그 지점부터 다시** |
| 끝이 안 보인다 | **진행률 표시** |

## 6-2. 두 개의 입구 — 자연어가 기본, 선택형이 보조

```
              ┌──────────────────────────────────────┐
              │  ① 어떻게 시작할까?          ★분기    │
              └────────┬────────────────────┬────────┘
            💬 말로 하기 (기본)       🔘 골라서 만들기 (보조)
              ┌────────▼────────┐            │
              │ ② 이해한 내용    │            │  말로 설명하기
              │    확인          │            │  어려운 분을 위한
              │  알아들은 항목은  │            │  경로
              │  질문을 건너뜀 ✨ │            │
              └────────┬────────┘            │
                       └──────────┬──────────┘
                             이후는 동일
```

핵심은 **슬롯 채우기(slot filling)** 다.
어느 입구로 들어와도 채워야 할 항목은 같고, 말에서 뽑아낸 것은 건너뛴다.

> `"우리 카페 신메뉴 크로플, 인스타에 올릴 사진 만들어줘"` 한 문장으로
> **무엇을·업종·규격·홍보 대상** 4개가 채워지고 질문 4개를 건너뛴다.

**설계 원칙 두 가지**

1. **못 알아들은 슬롯은 비워둔다.** 억지로 채우면 사장님이 말하지 않은 조건이 광고에 들어간다.
2. **근거를 보여준다.** `"인스타" 에서 규격을 잡았어요` 처럼 표시해 오인식을 사용자가 잡을 수 있게 한다.

                        ┌─────────▼─────────┐
                        │ ③ 무엇을 만들까?   │ ★분기
                        └────┬─────────┬────┘
                     📝 문구 │         │ 🖼️ 이미지
                   ┌─────────▼──┐ ┌────▼───────────┐
                   │ ④ 어떤 가게?│ │ ④ 어떤 가게?    │
                   │ ⑤ 제품 사진?│ │ ⑤ 제품 사진?    │ ★분기
                   └─────────┬──┘ │ ⑥ 참고 이미지?  │ ★분기
                             │    │   → 생성 모드 확정│
                             │    └────┬───────────┘
                   ┌─────────▼──┐ ┌────▼───────────┐
                   │ ⑦ 무엇을 홍보│ │ ⑦ 무엇을 홍보   │
                   │ ⑧ 어디에 쓸까│ │ ⑧ 어디에 쓸까   │
                   │ ⑨ 어떤 느낌 │ │ ⑨ 어떤 느낌     │

문구를 만들면 이미지에 올리고 싶어지기 때문이다.

┌───────────────────────┐   ┌───────────────────────────┐

└───────────┬───────────┘   └───────────┬───────────────┘
            └─────────────┬─────────────┘
                          ▼

          │  ③ 레이아웃 합성 (PIL)         │

**③ 레이아웃 합성을 분리해야 하는 이유**
Diffusion 모델은 한글을 제대로 그리지 못한다. 이미지는 "글자 없는 배경"으로 만들고
한글은 PIL 로 얹는 것이 유일하게 안정적이다.
덤으로 **문구만 바꿔 재출력**하는 것이 GPU 없이 즉시 가능해진다.

# 7. 설계 원칙

## 7-1. 3축 직교 분리 — 조합 폭발을 피한다

업종 N × 스타일 M × 규격 K 를 전부 만들면 조합 폭발이지만,
**세 축이 서로 독립적인 역할만** 담당하게 하면 정의는 `N + M + K` 개로 끝난다.

| 축 | 담당하는 것 | 담당하지 않는 것 |
|---|---|---|
| **업종** | 주제·배경 소재, 문구 페르소나, **적용 법령** | 색감, 치수 |
| **스타일** | 톤·조명·색상 팔레트, 문구 어조 | 무엇을 그릴지, 치수 |
| **규격** | 치수·안전영역·배치 규칙, 글자수 상한 | 그림 내용, 색감 |

```yaml
# configs/industries.yaml
- id: cafe
  label: 카페·디저트
  scene_prompt: "cozy cafe table, wooden surface, soft window light"
  copy_persona: "동네 단골에게 말 걸듯 따뜻하고 짧게"
  legal_tags: [general, food]     # 적용 법령 매핑
  status: verified                # verified | beta
```

`카페 × 따뜻한감성 × 인스타피드` 는 **런타임 문자열 합성**으로 만들어진다.
업종 추가는 YAML 10줄. **코드에 하드코딩된 업종 목록이 없다.**

### 배치 패턴은 규격마다 만들지 않고 4개를 공유한다

3장의 2축 분석에서 직접 도출된다.

| 패턴 | 설명 | 사용 규격 | 축 위치 |
|---|---|---|---|
| `bottom_band` | 하단 반투명 띠 + 헤드라인 | 인스타 피드, 배달앱 | 이미지 중심 |
| `top_bottom` | 상단 헤드라인 + 하단 정보 | 스토리, 전단지 | 중간 |
| `side_panel` | 이미지 60% + 우측 텍스트 | 가로 배너 | 중간 |
| `list_grid` | 항목·가격 반복 배치 | 메뉴판, 특가 POP | 정보 중심 |

### 검증 범위를 정직하게 관리한다

업종을 다 열면 각 업종의 품질을 검증할 수 없다. 그래서 `status` 로 구분한다.

- **`verified`** — 실제로 결과를 확인하고 프롬프트를 튜닝한 업종 (3~4개). 근거는 `results/` 에 남긴다
- **`beta`** — 정의만 해둔 업종. UI 에 `베타` 표시

## 7-2. 대화 흐름도 데이터로 둔다

질문 순서를 `if/elif` 로 짜면 순서 변경·질문 추가가 불가능해진다.
업종·스타일·규격을 YAML 로 뺀 것과 **같은 이유로 대화 흐름도 `configs/flow.yaml`** 에 둔다.

```yaml
- id: ask_format
  kind: choice
  ask: 어디에 쓰실 건가요?
  decides: 캔버스 크기 · 글자수 상한 · **옥외광고물법 적용 여부**
  store: format
  nl_fillable: true       # 자연어에서 채웠으면 질문을 건너뛴다
  source: formats         # 선택지를 레지스트리에서 자동 생성
  next: ask_style
```

`source: formats` 로 두면 **규격을 추가해도 flow.yaml 을 고칠 필요가 없다.**

## 7-3. 되돌아가기는 스냅샷으로

히스토리 항목마다 **답하기 직전 상태의 스냅샷**을 저장한다.
되돌리기는 스냅샷 복원 + 히스토리 자르기로 끝나므로 역방향 계산이 필요 없다.

# 8. 현재 구현 상태

모델이 미정이라 **생성 부분만 스텁**이고 나머지는 실제로 동작한다.

| 모듈 | 상태 | 내용 |
|---|---|---|
| `src/registry.py` | ✅ 동작 | YAML 레지스트리 로더 |
| `src/flow.py` | ✅ 동작 | 대화 상태 머신 · 슬롯 건너뛰기 · 되돌아가기 |
| `src/compliance.py` | ✅ 동작 | 금칙어 룰 엔진 · 적용 법령 · 원클릭 교체 |
| `src/layout.py` | ✅ 동작 | PIL 레이아웃 합성 (배치 4종 × 규격 6종) |
| `src/nlu.py` | 🔶 스텁 | 키워드 매칭 → **LLM 으로 교체 예정** |
| `src/image_gen.py` | 🔶 스텁 | 색보정 → **Diffusion 으로 교체 예정** |
| `src/copy_gen.py` | 🔶 스텁 | 템플릿 → **VLM + LLM 으로 교체 예정** |

- `app_chat.py` — 챗봇 흐름 **설계 데모** (실제 생성 없음, 팀 공유용)
- `app.py` — 초기 폼 방식 프로토타입 (비교용)

스텁 파일 상단에 **`━━ 실제 모델로 교체할 지점 ━━`** 주석이 있고,
`generate()` / `extract()` 내부만 갈아끼우면 호출부는 바뀌지 않는다.

`src/` 는 Streamlit 에 의존하지 않으므로 **프론트를 바꿔도 재사용된다.**

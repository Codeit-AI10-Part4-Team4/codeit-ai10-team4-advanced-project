## 0. 이 기능이 서비스 성격을 바꾼다

| | 이 기능이 없으면 | **있으면** |
|---|---|---|
| 서비스 정체성 | 예쁜 광고 만들어주는 도구 | **사고 안 나게 지켜주는 도구** |
| 대체재 | Canva, 미리캔버스 | 대체재 없음 |
| 소상공인 관점 | 있으면 좋은 것 | **모르면 과징금 맞는 것** |

소상공인이 광고 관련 법을 위반하는 건 **악의가 아니라 몰라서**다.
"다이어트에 좋은 샐러드", "동네 최고의 맛집" 같은 문구는 사장님 입장에서 자연스러운 표현이지만
각각 식품표시광고법·표시광고법 위반 소지가 있다.

**AI가 문구를 대신 써주는 서비스라면, 그 문구에 대한 책임 문제도 같이 안고 간다.**
따라서 이 기능은 차별화 요소인 동시에 **우리 서비스의 방어 장치**이기도 하다.

## 1. 소상공인이 실제로 걸리는 규제 지도

### 1-1. 전 업종 공통

**「표시·광고의 공정화에 관한 법률」 (표시광고법)** ✅ *원문 대조 완료*

- **제3조 (부당한 표시·광고 행위의 금지)** — 제1항 각 호에 4개 유형이 열거된다.
  **1호 거짓·과장 / 2호 기만 / 3호 부당하게 비교 / 4호 비방**
- **제5조 (표시·광고 내용의 실증 등)** — 사업자는 자기가 한 표시·광고 중
  **사실과 관련한 사항을 실증할 수 있어야** 한다. 공정위가 자료 제출을 요청하면
  **15일 이내**에 제출해야 한다.

| 위반 유형 | 소상공인 실제 사례 |
|---|---|
| 객관적 근거 없는 최상급 표현 | "동네 **최고**", "**1위**", "**최초**", "**유일**" |
| 거짓·과장 | 실제와 다른 사진, 부풀린 효능 |
| 기만 (중요 정보 은폐) | "**무료**" 인데 조건이 있음, 할인 조건 미기재 |
| 부당 가격 표시 | 정상가를 부풀린 뒤 할인율 표시 |
| 비방 | "옆집보다 신선한" 등 경쟁사 폄훼 |

> 최상급 표현을 쓰려면 공인기관 인증·시장점유율 데이터 등 **객관적 근거 자료를 구비**해야 한다.
> 자체 추산이나 임의 데이터는 허위·과장 광고로 간주된다.
> 위반 시 공정거래위원회의 시정명령·과징금·형사처벌 대상.

### 1-2. 음식점·카페 (식품 조리·판매)

**「식품 등의 표시·광고에 관한 법률」 제8조 (부당한 표시 또는 광고행위의 금지)** ✅ *원문 대조 완료*

제1항은 **10개 호**를 열거한다. 이 중 소상공인이 실제로 걸리는 것:

| 호 | 금지 유형 | 예시 표현 |
|:---:|---|---|
| **1호** | 질병의 예방·치료에 효능이 있는 것으로 인식할 우려 | "**혈압에 좋은**", "**면역력 강화**", "**염증 완화**" |
| **2호** | 식품등을 **의약품**으로 인식할 우려 | "**약**처럼 듣는", "**치료**" |
| **3호** | 건강기능식품이 **아닌 것**을 건강기능식품으로 인식할 우려 | **"다이어트"**, "체지방 감소", "**먹어도 살 안 찌는**" |
| **4호** | 거짓·과장된 표시·광고 | "**단기간 급속 감량**", "**지방이 배출된다**" |
| 5호 | 소비자를 기만 | |
| 6호 | 다른 업체·제품 비방 | |
| 7호 | 객관적 근거 없이 부당하게 비교 | |

> ⚠️ **"다이어트"는 소상공인이 가장 흔히 쓰면서 가장 잘 걸리는 단어다.**
> 기능성이 인정되지 않은 일반 식품에 체중 조절 관련 문구를 쓰는 것은
> 건강기능식품으로 오인케 하는 표시·광고로 금지된다.
> 샐러드 가게·주스 가게 사장님이 무심코 쓰는 표현이라 우리 서비스에서 반드시 잡아야 한다.

**추가 적용 가능 법령**
- 「농수산물의 원산지 표시 등에 관한 법률」 — 음식점 원산지 표시 의무
- 가격표시제 (음식점 옥외가격표시제)

### 1-3. 매체별 — 옥외 광고물

**「옥외광고물 등의 관리와 옥외광고산업 진흥에 관한 법률」 제3조** ✅ *원문 대조 완료 — 초안 정정*

허가와 신고는 **광고물 종류에 따라 갈린다.** 초안은 이를 뭉뚱그렸다.

| 광고물 | 절차 |
|---|---|
| 입간판·현수막·벽보·**전단**을 **제외한** 광고물 | **허가** |
| 현수막·벽보·**전단** | **신고** (시·군·구 조례로 신고증명서 발급을 갈음 가능) |
| 면적 30㎡ 초과 현수막 게시시설 | 신고 대상 |

> 우리 서비스의 **전단지·메뉴판(인쇄) 규격은 "신고" 계열**이다.
> 사용자에게는 "허가받으세요"가 아니라 **"게시 전 관할 지자체에 확인하세요"** 로 안내해야 정확하다.

> 우리 서비스에서 **전단지·현수막 규격을 선택하면 이 법이 활성화**된다.
> 온라인 규격(인스타 등)에는 적용되지 않는다.
> → `formats.yaml` 의 `legal_tags` 로 분기하는 이유.

## 2. 설계 원칙 — 왜 "사후 검사만"으로는 부족한가

원래 아이디어는 **광고 생성 후 버튼을 누르면 근거가 뜨는** 방식이었다.
설명 UX로는 이게 정확하다. 다만 이것만 있으면 문제가 생긴다:

> 생성된 문구에서 위반이 발견되면 **사용자는 뭘 해야 하나?**
> 다시 만들라고? 그럼 왜 처음에 위반 문구를 만들어줬나?

그래서 **3단계로 나눈다.**

```
┌──────────────────────────────────────────────────────────────┐
│  Stage A · 생성 전 — 제약 주입 (Prevention)                   │
│  업종·규격에 해당하는 금지 규칙을 문구 생성 프롬프트에 주입   │
│  → 애초에 위반 문구가 생성되지 않는다                         │
│  → [01 문서] P0-4 에 해당                                     │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  Stage B · 생성 후 — 검증 (Detection)                         │
│  생성된 문구를 스캔해 위반 후보 감지                          │
│  → 룰 기반 사전 매칭 (즉시, 정확)                             │
│  → 위반 시 대체 표현 제안 + [바꾸기] 버튼                     │
└───────────────────────────┬──────────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  Stage C · 요청 시 — 설명 (Explanation)  ★원래 아이디어       │
│  [⚖️ 이 광고, 법적으로 괜찮나요?] 버튼 클릭                    │
│  → RAG 로 적용 법령·조문·근거 검색                            │
│  → "어떤 규정을 받고, 어떻게 지켰는지" 패널 표시              │
│  → [01 문서] P1-9 에 해당                                     │
└──────────────────────────────────────────────────────────────┘
```

**Stage A 가 있어야 Stage C 가 자랑거리가 된다.**
A 없이 C만 있으면 "위반입니다" 경고만 띄우는 서비스가 되고,
A가 있으면 C는 **"우리가 이미 이렇게 지켜서 만들었습니다"** 라는 신뢰 장치가 된다.

## 3. 아키텍처 — 룰 기반 + RAG 하이브리드

**RAG 단독으로 가면 안 된다.** 두 가지를 분리한다.

| 담당 | 방식 | 이유 |
|---|---|---|
| **금칙 표현 탐지** | 사전(dictionary) + 정규식 매칭 | "최고", "1위", "다이어트", "치료" 같은 **확정적 금칙어**는 룰이 빠르고 정확하다.<br>LLM에 맡기면 놓친다. **응답 속도 평가에도 유리** (즉시 반응) |
| **왜 안 되는지 설명<br>+ 조문 근거<br>+ 유사 사례** | RAG (벡터 검색) | 법령 원문·심사지침·처분 사례에서 근거를 끌어와야 하는 영역.<br>여기가 RAG의 본령 |

```
                    생성된 광고 문구
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
┌──────────────────────┐      ┌──────────────────────────┐
│  룰 엔진              │      │  RAG 파이프라인           │
│                      │      │                          │
│  금칙어 사전 매칭     │      │  쿼리 = 문구 + 업종      │
│  정규식 패턴          │─────▶│  메타 필터 = legal_tags  │
│  (즉시, ~10ms)       │ 히트 │  ↓                       │
│                      │ 표현 │  하이브리드 검색          │
│  → 위반 후보 목록     │      │  (BM25 + dense + RRF)    │
│  → 대체 표현 제안     │      │  ↓                       │
└──────────────────────┘      │  LLM: 근거 요약 생성      │
                              └──────────────────────────┘
```

### 이전 프로젝트 자산 재사용

`rfp-rag-extractor` 에서 검증한 구성을 그대로 가져올 수 있다.

| 구성요소 | 재사용 근거 |
|---|---|
| 하이브리드 검색 (BM25 + dense + RRF) | **법령 검색은 정확한 용어 매칭이 결정적**이라 BM25가 특히 유효.<br>"제3조", "부당한 표시·광고" 같은 정확 매칭이 dense만으로는 약함 |
| bge-m3 임베딩 | 한국어 검색에서 검증 완료 |
| 임베딩·LLM·벡터스토어 추상화 계층 | `.env` 만 바꿔 전환 가능한 구조 그대로 |

> 이건 **일정상 큰 이점**이다. RAG를 처음부터 만드는 게 아니라 검증된 구조를 옮겨오는 것.

## 4. 코퍼스 구성

| 문서 종류 | 출처 | 청킹 단위 |
|---|---|---|
| 법령 조문 | 국가법령정보센터 (law.go.kr)<br>표시광고법 / 식품표시광고법 / 옥외광고물법 / 원산지표시법 / 학원법 / 체육시설법 | **조(條) 단위** |
| 공정위 고시·심사지침 | 「부당한 표시·광고행위의 유형 및 기준 지정고시」<br>「추천·보증 등에 관한 표시·광고 심사지침」 | 항목 단위 |
| 식약처 가이드 | 식품안전나라 부당 표시·광고 안내, 적발 사례 | 사례 단위 |

### 메타데이터 스키마

검색 시 **업종·매체로 필터링**해야 정확도가 나온다. 문구만 넣고 전체 검색하면 엉뚱한 법령이 나온다.

```yaml
# 코퍼스 청크 메타데이터
law_name: "식품 등의 표시·광고에 관한 법률"
article: "제8조"
legal_tags: [food]          # general | food | outdoor | academy | fitness | alcohol | medical
media: [online, offline]    # 적용 매체
severity: high              # high | medium | low
```

`industries.yaml` 의 `legal_tags` × `formats.yaml` 의 `legal_tags` 로 **검색 범위를 사전 축소**한다.

```
카페 (legal_tags: [food, general])  ×  전단지 (legal_tags: [offline, outdoor])
        └───────────────┬───────────────┘
                        ▼
        검색 필터: legal_tags ∈ {food, general, outdoor}
        → 학원법·체육시설법 조문은 애초에 검색 대상에서 제외
```

### UX 원칙

| 원칙 | 이유 |
|---|---|
| **기본은 접혀 있고, 눌러야 펼쳐진다** | 사장님이 광고 만들러 왔지 법률 공부하러 온 게 아니다. 방해하면 안 됨 |
| **위반 발견 시 "대체 표현 + 원클릭 교체"** | 문제만 알려주고 해결을 안 주면 무용지물. 레이아웃 분리 덕에 GPU 재실행 없이 즉시 반영 |
| **✅ 지킨 것을 먼저, ⚠️ 문제를 나중에** | 원래 아이디어의 핵심. "이래서 이렇게 만들었다"는 **신뢰 메시지**가 먼저 와야 한다 |
| **면책 고지 상시 노출** | 법률 자문으로 오인되면 우리가 책임진다 |

## 7. 일정 리스크와 축소 시나리오

이 기능을 넣으면 파이프라인이 **3개**가 된다 (이미지 / 문구 / RAG).
중급 프로젝트 기간 내에 전부 완성하지 못할 가능성을 미리 대비한다.

| 단계 | 범위 | 난이도 | 없으면? |
|---|---|---|---|
| **최소** | 금칙어 사전 + 룰 매칭 + 생성 프롬프트 주입 (Stage A + B) | 낮음 | 이것만으로도 "법을 지키는 AI"라고 말할 수 있다 |
| **표준** | 위 + 법령 코퍼스 RAG 설명 패널 (Stage C) | 중간 | **목표 지점** |
| **확장** | 위 + 처분 사례 검색, 조문 원문 링크, 업종별 체크리스트 | 높음 | 여유 시 |

> **최소 단계는 GPU도 벡터DB도 필요 없다.** YAML 사전 하나로 구현된다.
> 따라서 **먼저 최소 단계를 완성해두고**, RAG는 그 위에 얹는 순서로 간다.
> 이러면 일정이 밀려도 기능이 통째로 날아가지 않는다.

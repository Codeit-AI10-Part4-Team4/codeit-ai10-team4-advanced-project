## 경계

기본 파이프라인(`generation`) 코드를 **import 하지 않는다.** 계약은 아래 하나뿐이다.

```
evaluate(image, headline, sub, items, context) -> EvaluationResult
                                                       └─(suggestions)─> 재생성
```

반대 방향도 함수 하나로만 부른다. 이 경계가 흐려지면 두 파트가 서로를 기다리게 된다.

내부 경계는 `build_features(address, category) -> TradeAreaFeatures` 하나다.
이 함수 앞이 아인님, 뒤가 수호님이다.

## 설계 결정 — 코드만 봐서는 안 보이는 것

**정량은 코드, LLM은 서사만.** 세그먼트·가중치·집계·근거 대조는 전부 결정적 코드다.
LLM은 `narrative`와 평가 문장만 만든다. 신뢰 판단의 근거는 모델의 자기보고가 아니라
코드 검증 결과여야 하기 때문이다. `evidence.py`가 그 집행 지점이다.

**경계 페르소나는 점수에서 빼고 코멘트·저항 요인에는 남긴다.**
06 §7.1의 "점수 기여가 아니라 저항 요인·코멘트 다양성 목적"을 그대로 구현했다.
뺀 만큼 가중치를 재정규화한다. `include_boundary_in_scores=True`로 뒤집을 수 있게
열어둔 것은 비교 실험용이다.

**성별과 연령이 한 축이 아니라 두 축이다.**
서울시 원본에 성별×연령 교차 데이터가 없다(07 §4.4①). "30대 여성 매출"이라는
값 자체가 존재하지 않아 두 축을 따로 두고 페르소나에서 곱한다. 그래서 `evidence`도
곱한 값이 아니라 원본 두 값을 각각 인용해야 대조가 1:1로 맞는다.

**시간대는 유동인구가 아니라 매출 기준이다.**
지나다니는 사람과 사는 사람이 다르다(07 §4.4③). 유동인구는 `foot_age_share`,
동네 주민은 `back_age_share`로 남겨 경계 페르소나 근거로 쓴다.
`back_age_share`는 골목상권에만 있어 발달상권(역삼역)에서는 `None`이다 —
매핑이 `None`일 수 있으므로 `resolve()`에 방어가 들어 있다.

**상권 성격은 추론이 아니라 실측이다.**
`motive` 판정이 "점심에 팔리니 직장인 상권"이라는 추론에서 `work_ratio` 실측으로
바뀌었다(07 §7.1). `worker_pop`·`resident_pop`·`apt_avg_price` 등을 스키마에
두지 않으면 Pydantic이 조용히 버려서 평가 프롬프트에 넣을 수가 없다.

**`axes.time` enum이 5종이다.**
`morning / weekday_lunch / afternoon / evening / weekend`. `weekend`는
`weekend_ratio > 0.4`일 때만 나온다(역삼역 0.138이라 없음).
`Persona.axes`를 `dict[str, str]`이 아니라 모델로 고정했기 때문에 값이 검증된다.

**`is_fallback` / `match_distance_m`은 07 §6에 없는 추가 필드다.**
06 §5가 "서울 평균 폴백 시 결과 화면에 배지"를 요구하는데 그 플래그가 없었다.
기본값이 있어 A쪽이 안 채워도 파싱은 된다.

**신뢰도를 떨어뜨리는 사유가 셋이고, 화면 문구가 달라야 한다.**
폴백(동네 데이터 없음) · `demo_coverage < 0.5`(미상 매출 과다, 07 §4.4②) ·
분산 초과(손님별 평가가 갈림). 셋을 한 플래그로 뭉치면 사장님에게 무엇이
문제인지 못 알려주므로 `confidence_reasons`에 사유를 따로 남긴다.
**업종 폴백은 여기 넣지 않는다** — 정밀도만 낮아질 뿐 "우리 동네" 그라운딩은
유지되고(07 §4.5), `realestate`처럼 커버리지 1%인 업종은 폴백이 기본이라
항상 "신뢰도 낮음"이 뜨면 배지가 무의미해진다.

**매칭·데이터 품질 지표는 근거로 인용할 수 없다.**
`match_distance_m` · `demo_coverage`. 상권 특성이 아닐뿐더러, 이런 수치로도
근거 요건이 충족되면 LLM이 실제 인구·행동 데이터를 보지 않고 검증 게이트를
통과한다 — 게이트의 목적이 무너진다. 실패 사유는 `unknown_path`가 아니라
`not_citable`로 구분해 로그에서 오타와 정책 위반을 가른다.

**`aggregate()`는 `suggestions`를 만들지 않는다.**
개선 제안은 집계가 아니라 요약 콜의 산출물이라(07 §7.3) 인자로 받아 실어 나르기만
한다. 07 §7이 "패널 모듈 LLM 콜은 서사 1콜 + 평가 ≤20콜 둘뿐"이라 했는데 제안을
만들 콜이 명세에 없어서 `evaluator` 가 집계 뒤 1콜을 더 쓴다. 아인님 합의 전까지
`evaluate(..., summarize=False)` 로 끌 수 있다.

**병렬은 asyncio 가 아니라 스레드다.**
`ChatClient.complete_json` 이 동기라 asyncio 를 쓰려면 공용 `app_core/llm.py` 에
async 를 더해야 한다. API 호출은 IO 바운드라 스레드로 충분하고, 스텁 프로필
테스트도 그대로 돌아간다. 07 §8 의사코드와 형태만 다르고 동작은 같다.

**두 관문의 실패가 모두 `excluded_cnt` 에 잡혀야 한다.**
스키마·근거 재시도까지 실패한 페르소나는 `evals` 에 들어오지도 못한다.
`aggregate(failed_ids=...)` 로 넘기지 않으면 투명성 지표가 앞단 실패를 놓쳐
"탈락 0건"이라는 거짓말을 한다.

**평가 프롬프트에는 인용 가능한 숫자만 넣는다.**
`match_distance_m`·`demo_coverage` 를 프롬프트에 주면 모델이 그걸 인용하고
전량 `not_citable` 로 탈락한다. 페르소나 자신의 근거 + 상권 공통값만 준다.

## 규칙

- `schemas.py`는 수호 단독 소유다(07 §12). 아인님 요청은 받되 편집은 수호가 한다.
- `docs/`·픽스처·`features.py`·`panel_builder.py`는 아인님 소유다. 고치지 말고 요청한다.
- `configs/*.yaml`·`flow.yaml`은 기본 파이프라인 소유다. 업종 추가가 필요하면 PR 전에 공유.
- 외부 API 호출은 테스트에서 mock. 실 호출은 비용·비결정성으로 금지.
- 파일을 추가·변경하면 **아래 표에 한 줄 추가하고 상단 버전을 올린다.**

**프롬프트의 자리표시자는 실제로 쓸 수 있는 값이어야 한다.**
`"resistance": "price|message|relevance|none"` 처럼 "이 중 택1"의 뜻으로 쓴 세로줄을
모델이 **그대로 베낀다.** 실측(아인님, 2026-08-11): 23콜 중 21콜이 이렇게 나와
스키마에서 탈락했고 12명 중 1~5명만 살아남아 제품 전체가 막혔다. 허용값은 예시가
아니라 문장으로 적는다. **부정 예시("price|message 는 틀림")도 쓰지 않는다** — 베끼는
대상이 그 문자열이라 역효과가 난다. `"attention": 0` 같은 자리표시자도 같은 이유로
쓰지 않는다(0점 쪽으로 끌린다).

**`temperature=0` 에서 재시도가 의미를 가지려면 입력이 달라져야 한다.**
같은 프롬프트를 다시 보내면 같은 오답이 나와 비용만 두 배가 된다. 무작위성을
올리는 대신 **무엇을 어겼는지 알려준다** — 교정 확률이 높고 점수 재현성도 유지된다.

**대조(`contrast`)는 결과에 실어 보낸다.**
화면이 `EvaluationResult` 하나만 보면 되도록 설계했으므로, 여기 없으면 화면이
`contrast()` 를 따로 부르며 features 를 다시 들고 다녀야 한다. LLM 을 안 쓰므로
콜 예산에 영향이 없고, 페르소나 평가가 흔들려도 이 문장들은 흔들리지 않는다.

**저항 요인은 라벨만으로 부족하다.**
`top_resistance` 는 순서만 주고 크기를 안 준다. 화면이 "가격 74% · 관련성 26%"를
쓰려면 비중이 필요해서 `resistance_share` 를 더했다. `none` 은 뺀 값이라 합이 1 이다.

## 방어 설계 (V5) — 스스로 공격해서 뚫린 8곳을 막았다

"이 모듈은 어디가 약한가"를 코드로 직접 공격해 확인한 뒤 막은 것들이다.
전부 공격 재현 테스트로 고정되어 있어 재발하면 CI 가 잡는다.

**입력이 거짓말을 못 하게.**
NaN 은 모든 비교가 거짓이라 비중 합계 검사를 통과해 버리고, {-0.5, 1.5} 는
합이 정확히 1 이라 합계만 봐서는 못 잡는다. 비중은 값 하나하나가 0~1 의
유한한 수인지 본다. `FeatureRef` 의 NaN 도 입구에서 끊는다 — 대조가 조용히
항상 실패하면 로그에서 "왜 늘 탈락하지"를 오래 헤매게 된다.

**호출 하나의 실패는 그 손님 한 명으로 끝나게.**
스레드 안 예외는 `Future.result()` 에서 다시 터진다 — 방벽이 없으면 네트워크
순단 한 건이 통과한 11명의 결과까지 통째로 버린다(실측으로 확인). 요약 콜
실패도 같다: 부가물이 본체를 죽이면 안 된다.

**마감(deadline)은 실제로 지켜진다.**
07 R4 의 30초 예산에서 25초를 평가 마감으로 잡고, 넘긴 페르소나는 실패로
세고 신뢰도 사유에 남긴다. `with ThreadPoolExecutor` 를 쓰지 않는 이유:
블록을 나갈 때 실행 중인 스레드를 기다려서 마감이 마감이 아니게 된다.
소요 시간은 `elapsed_ms` 로 결과에 실려 예산 준수를 스스로 증명한다.

**점수가 대표성을 잃으면 결과가 스스로 말한다.**
탈락이 몰려 3명 미만만 남으면 "표본이 작음", 재정규화 후 한 명이 절반을
넘으면 "쏠림" — 그 점수는 패널이 아니라 개인의 취향이다. 같은 페르소나의
중복 응답은 첫 응답만 쓴다(두 번 세면 가중치가 두 배가 된다).

**고칠 수 있는 위반은 재시도(유료)로 보내지 않는다.**
모델이 `persona_id` 를 에코하면 벗겨내고(서버 값이 이긴다), 폭주 텍스트는
300자에서 자른다. 스키마의 400자 상한은 마지막 방벽이다.

## 정확도 설계 (V6) — 거르는 것과 맞추는 것은 다르다

V5 까지는 **틀린 응답을 거르는** 장치였다. 거른다고 남은 답이 맞는 것은 아니다.
정확도를 올리려면 세 가지를 따로 봐야 한다 — 근거의 질, 척도의 안정성,
그리고 무엇보다 **잴 수 있는가**.

**근거는 "값이 맞다"가 아니라 "내 것이다"여야 한다.**
값의 정확성만 보면 60대 손님이 `age_share.30`(30대 38.2%)을 근거로 대도 통과한다.
인용은 정확하지만 자기 판단의 근거는 아니다. 그 손님에게 **실제로 보여준 경로만**
인정한다(`offered_paths`). 프롬프트와 게이트가 같은 함수를 보므로 따로 관리하다
어긋날 일이 없고, 어긋나면 `test_offered_paths_match_the_prompt` 가 잡는다.

**0~100 만 주면 척도가 사람마다 다르다.**
LLM 의 절대 점수는 앵커가 없으면 표류하고 60점대에 몰린다. 구간마다 뜻을 준다
(`0~20 그냥 지나친다` … `81~100 지금 가고 싶다`). 앵커는 판별력을 만드는 장치다 —
좋고 나쁨의 간격이 벌어져야 순서를 가릴 수 있다.

**같은 답을 한 번 더 물어본다.**
같은 광고 3회에 53.4 / 53.5 / 63.4 (실측, 아인님). `temperature=0` 도 `seed` 도
막지 못한다. 여러 번 물어 **중앙값**을 쓰면 한 번의 튐이 결과를 못 흔든다
(평균이면 63 에 끌려간다). 전원 3회는 예산을 넘으므로 **가중치가 큰 손님부터**
남는 콜만큼 반복한다 — 역삼역 기준 상위 3명이 가중치의 49.5% 를 갖는다.
합성 문장은 만들지 않는다: 중앙값에 가장 가까운 **실제 응답**의 코멘트를 쓴다.

**그리고 잴 수 있게 만들었다 (`eval/accuracy.py`).**
"실제 손님 반응"이라는 정답은 우리에게 없다. 정답 대신 **순서**를 쓴다 — 사람이면
이견 없이 답할 수 있는 광고 쌍을 역삼 실측에서 만들고(점심 47.9% vs 새벽 0.1%,
객단가 9,546원 vs 45,000원, 30대 38.2% vs 10대 겨냥), 패널이 그 순서를 맞추는지 본다.
**판별력이 낮으면 절대 점수는 노이즈다** — 이 지표가 먼저다.

상권 근거 쌍과 보편 쌍(명료성)은 **따로 집계한다.** 섞으면 틀렸을 때 "동네 데이터가
안 쓰인다"인지 "기본기 문제"인지 구분하지 못한다. 사람 평가 대조(블라인드 시트 →
스피어만 상관)도 같은 파일에 있다.

| 버전 | 날짜 | 변경 | 이유 |
|---|---|---|---|
| **V6** | 2026-08-11 | ① 근거를 `offered_paths` 로 제한(`off_prompt`) ② 점수 구간 앵커 ③ 자기일관성 — 가중치 순 중앙값(`consistency_k`) ④ `eval/accuracy.py` 판별력·사람대조 하네스 | 거르는 것만으로는 정확도를 말할 수 없다. 근거의 질·척도 안정성을 올리고, 무엇보다 **잴 수 있게** 만들었다 |

## V7 — 제안이 금액을 지어내던 것 (아인님 실측, 2026-08-11)

광고는 6,000원인데 제안이 "9,500원에서 8,500원으로 조정해보세요"라고 나왔다.
같은 입력 3회에 3회 다 지어냈다. **손님 12명은 6,000원을 정확히 쓰고 있었으니
요약 콜만의 문제였다.**

원인은 프롬프트의 "좋은 예"였다 — `'런치 세트 8,900원'`. 그 8,900원은 어디에도
없는 금액이고 모델은 **그 행동을 배웠다.** `resistance` 세로줄 사고와 같은 부류다.
**자리표시자·예시는 실제로 쓸 수 있는 값이어야 한다.**

**페르소나 응답은 근거 대조를 거치는데 제안만 그냥 통과했다.** 검증받지 않은
숫자가 사장님 화면에 뜨는 것은 표시광고법 문제이기도 하다. 이제 두 겹으로 막는다 —
프롬프트에 실제 가격·객단가를 주어 **지어낼 이유를 없애고**, 그래도 다른 금액이
나오면 **그 제안을 버린다**(실제 가격·객단가는 인용 가능).

우리는 가격을 제안하지 않는다. **가격을 어떻게 보여줄지**를 제안한다 —
01 문서의 "가격은 AI 가 생성하지 않고 사장님이 직접 입력"과 같은 원칙이다.

| 버전 | 날짜 | 변경 | 이유 |
|---|---|---|---|
| **V7** | 2026-08-11 | 요약 프롬프트에서 가짜 금액 예시 제거, 실제 가격·객단가 제공, 제안 금액 화이트리스트 게이트 | 리뷰 중인 PR 에 살아 있던 버그. 검증받지 않은 금액이 사장님 화면에 뜰 수 있었다 |

## V8 — 실제 API 로 재고 고친 하루 (2026-08-11)

`eval/accuracy.py` 로 역삼역 실측 광고 쌍을 돌려 **상권 쌍 평균 점수차**를
지표로 삼았다. 판별 자체는 처음부터 4/4 였지만, 점수차가 작으면 순서만 맞고
실제로는 구별 못 하는 것에 가깝다.

| 판 | 상권 평균 |
|---|---|
| 계측 보강 직후 | +11.7 |
| `standing` 추가 | **+20.3** |
| 기본값 `none` 실험 | +17.4 (되돌림) |
| 집계 필터 | +18.1 |

`standing` 이후 세 번 재현: 시간대 7.4 · 가격 35.1 · 타깃 13.4 (폭 3~7).

### 가장 큰 발견 — "12명 패널"이 사실상 1명이었다

계측기가 평균 하나만 찍고 있어서 안 보였다. **지표별·손님 편차**를 갈라 찍자
드러났다 — 주목·방문의향의 차이가 **정확히 `+0.0`**, 손님 편차 **0.0**.
12명이 한 명도 빠짐없이 같은 점수를 냈다는 뜻이다.

아인님의 "코멘트 의미가 같다", "걸림돌 전원 `price`", 내 "좋은 쪽이 전부 55" 가
**전부 같은 현상**이었다. 각자 다른 증상으로 보고 있었다.

`standing()` 으로 자기가 이 동네에서 어떤 위치인지(핵심 고객 / 평범 / 놓치는 층)를
문장으로 주자 손님 편차가 **3.01 → 7.67** 로 살아났다(절제 실험). 아인님이
같은 취지로 **수치**를 넣었을 때는 안 움직였다 — 숫자를 던지는 것과 2인칭으로
판정해주는 것이 달랐다.

### 실패한 것도 남긴다

- **광고가 말한 시간대를 근거로 제공** — +2.3 → +2.6. 노이즈(3점) 안이라 효과 없음.
  해롭지도 않고 근거상 옳아서 남겨뒀지만, 이것만으로는 시간대 쌍이 안 살아났다.
  나중에 `standing` 이 들어가고서야 +8.4 로 올랐다.
- **걸림돌을 프롬프트로 고치기 — 네 번 실패.** 처지에 묶기 · `intent` 임계값 ·
  기본값 `none` · 집계 필터. 좋은 광고에서 여전히 `price` 100% 다.

### 걸림돌은 알려진 한계다 (화면에서 크게 쓰지 말 것)

원인이 잡혔다. **모델이 척도 상단을 안 쓴다** — 좋은 쪽 절대 점수가 네 번의
실행 16개 값에서 **53.4~60.9** 였고 앵커의 "61~80 한번 가볼까"를 한 번도
넘지 않았다. 그래서 `RESISTANCE_INTENT_MAX = 60` 필터가 발동할 일이 없었다.

필터 자체는 원칙상 맞다(가겠다는 손님의 흠은 발길을 돌린 이유가 아니다) —
남겨두되, **`top_resistance` 를 화면 전면에 쓰지 않기를 권한다.** 다만
"나와 상관없다"가 걸리는 경우는 실제로 잡힌다: 10대 겨냥 광고에서
`relevance` 가 42~73% 로 나온다. 관련성 축은 살아 있고 가격 축이 죽어 있다.

|---|---|---|---|
| **V8** | 2026-08-11 | `standing()` 도입, 걸림돌 집계 필터(`RESISTANCE_INTENT_MAX`), 실패한 시도 기록 | 실제 API 측정으로 상권 평균 점수차 +11.7 → +18~20. "12명이 1명이었다"를 찾아 고침 |
